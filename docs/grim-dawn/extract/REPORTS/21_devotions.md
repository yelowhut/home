# Отчёт 21 — Девоушены (созвездия)

Скрипт: `docs/grim-dawn/extract/21_devotions.py`
Выход: `data/grim-dawn/devotions.json` (381 775 байт, ~373 KB)

Скрипт уже существовал от прошлого захода (был прерван внешне). В этом заходе я не
переписывал его с нуля — прочитал, прогнал, проверил на реальных данных, нашёл
и исправил три конкретных изъяна (см. «Что было исправлено»), заново прогнал,

## Как устроен резолв (для справки — уже было в докстринге скрипта, подтверждено)

```
records/ui/skills/devotion/constellations/constellationNN.dbr   (тип '', НЕ Skill_*)
    .devotionButtonK  -> records/ui/skills/devotion/tierT_NNx.dbr   (UI-кнопка, тип '')
        .skillName    -> records/skills/devotion/tierT_NNx[_skill].dbr  (сам узел)
            type == 'Skill_Passive'  -> узел-стат
            иначе                     -> узел-небесная сила (celestial power)
```

- Порядок узлов = число K в `devotionButtonK`.
- Ветвление (созвездия типа Ulzuin's Torch, где путь не линеен) — поле
  `devotionLinksK` на созвездии: `devotionLinksK = J` означает «узел K соединён с
  узлом J». Проверено: во всех 109 созвездиях граф parent→child консистентен
  (нет узла, ссылающегося на несуществующего или более позднего родителя — проверил
  скриптом на всём выходе, 0 аномалий).
- Триггер небесной силы — `templateAutoCast` на узле ведёт к отдельной записи
  `records/controllers/itemskills/cast_@....dbr` с `triggerType/targetType/
  chanceToRun/autoTargetRadius`.

## Схема выхода JSON

```
{
  "affinities": [ {num, name, name_tag, desc, desc_tag, color_rgb{r,g,b}} × 5 ],
  "meta": { constellations, constellations_skipped, total_nodes, stat_nodes,
            power_nodes, devotion_shrine_dbr_templates,
            max_devotion_points, max_devotion_points_source,
            total_devotion_points_note },
  "constellations": [
    {
      record, number, name, name_tag, desc, desc_tag, tier,
      points_cost,               # = число узлов = сумма стоимости в очках девоушена
      affinity_required: {Affinity: N},   # из affinityRequiredNameI/affinityRequiredI
      affinity_given: {Affinity: N},      # из affinityGivenNameI/affinityGivenI
      nodes: [
        { index, parent_index, record, kind: "stat"|"power",
          stats: {...},        # kind=stat: очищенные ненулевые поля .dbr узла
          power: {             # kind=power
            name, name_tag, desc, desc_tag, skill_class,
            cooldown, duration, instant_cast,
            trigger: {record, trigger_type, target_type, chance_pct, radius} | null,
            attach_blacklist: [...],   # скиллы, к которым силу НЕЛЬЗЯ привязать
            effect: {...}       # остальные ненулевые поля силы (урон/радиус/пр.)
          }
        }, ...
      ]
    }, ...
  ]
}
```

Поле `petBonusName` (внутри `stats`/`effect`) резолвится в
`{"record": path, "stats": {...}}` — реальные цифры бонуса, который получает
активный питомец игрока, а не голый путь.

## Что было исправлено в этом заходе

1. **`maxDevotionPoints` — было выброшено, хотя есть в БД.** Старая версия
   писала в отчёт/выход «число 55 не проверено, community-цифра, не факт».
   Нашёл авторитетную игровую константу: `records/creatures/pc/playerlevels.dbr`
   → `maxDevotionPoints = 55`. Теперь это в `meta.max_devotion_points` с явным
   указанием источника поля (`max_devotion_points_source`), а не голословное
   «обычно 55».
2. **`petBonusName` резолвился как путь-строка, а не как реальные цифры.**
   97 узлов ссылаются на `*_petbonus.dbr` (шаблон `petbonus.tpl`, ~350 полей,
   почти все нулевые). Проверил на 3+ записях: там лежит бонус, который
   получает **питомец игрока** (не сам игрок), пока открыт этот узел —
   например, у Hawk (узел 2) собственно игрок получает
   `offensiveCritDamageModifier: 5.0`, а его питомцы **отдельно** получают тот
   же бонус через petbonus-запись. Раньше в JSON было просто
   `"petBonusName": "records/skills/devotion/tier1_27b_petbonus.dbr"` — теперь
   резолвится в `{"record": ..., "stats": {"offensiveCritDamageModifier": 5.0}}`.
3. **Опечатка в самой игре не ловилась regex'ом.** Один файл называется
   `tier1_31d_perbonus.dbr` (потеряна буква `t` — `pet`→`per`), и ссылка на
   него в другой записи указывает именно на опечатанное имя. Старый паттерн
   `LIKE '%_petbonus.dbr'` его не находил → оставался нерезолвленным. Расширил
   запрос до `LIKE '%petbonus.dbr' OR LIKE '%perbonus.dbr'`. Это опечатка
   разработчиков GD, не наша — просто нужно было её поймать.

Всё остальное в скрипте (резолв кнопок/узлов, ветвление, `templateAutoCast`,
чёрный список аффиксов, справочник аффинити с цветами) проверил и подтвердил —
работает корректно, семантика не выдумана, а проверена по нескольким записям.

## Что не удалось / в чём не уверен

1. **Массивы значений по 15 элементов в `effect` некоторых небесных сил**
   (например, `offensiveFireMax`/`offensiveFireMin` у Meteor Shower — 15 чисел
   каждое) — не понял, по какой оси они масштабируются. `skillMaxLevel` у этих
   узлов = 1, то есть это не "уровень скилла" в обычном смысле. Похоже на
   таблицу масштабирования по чему-то ещё (уровень персонажа? какой-то внутренний
   ранг?), но я не нашёл в статическом дампе поле, которое явно связывало бы
   индекс массива с конкретной величиной. **В выходе массив сохранён как есть,
   без придуманной интерпретации** — при использовании этих цифр для билд-калькулятора
   это нужно перепроверить отдельно (возможно, через сравнение с логом реальной игры
   на разных уровнях персонажа).
2. **Как физически выдаются 55 очков девоушена (святилища + квесты) — не
   восстановлено.** Нашёл константу `maxDevotionPoints=55` (авторитетно), но
   разбивку "сколько от святилищ / сколько от квестов" из статического дампа
   `.dbr` собрать не удалось: шаблонов `devotionshrine*.dbr` в БД 69, но это
   шаблоны объектов (разные визуальные варианты одного святилища), а не
   гарантированно число реально расставленных на картах экземпляров; награды
   девоушен-очков за квесты нигде не просуммированы одним полем, который я бы
   нашёл (только UI-обвязка типа `questrewardwindow`, без самих чисел по каждому
   квесту). Если это важно для дальнейшей работы — нужен отдельный проход по
   quest-записям.
3. **11 из 63 небесных сил не имеют `trigger`** (пример: Assassin's Mark у
   Assassin's Blade, Rend у Huntress, ауры типа Menhir's Obelisk/Tree of Life/
   Bard's Harp). Проверил: у всех них попросту нет поля `templateAutoCast`, то
   есть они не проковые (не привязываются как рандомный шанс к скиллу), а
   являются либо постоянными модификаторами атаки (`Skill_AttackBuff` —
   применяются на каждой атаке безусловно), либо ауры вокруг игрока
   (`Skill_BuffRadius`, работают постоянно, без "привязки к скиллу" вообще).
   Это осознанное решение схемы (`trigger: null` = не проковая сила), а не баг,
   но стоит иметь в виду при использовании выхода — не путать "нет триггера" с
   "не резолвилось".
4. **`skillBlackList` = "к каким скиллам НЕЛЬЗЯ привязать силу"** — гипотеза
   проверена на 6+ разных записях (везде это стабильный список из
   teleport/disengage-рун), совпадает с известным игровым ограничением
   (девоушен-проки нельзя вешать на скиллы телепортации/рывка). Уверен в этой
   интерпретации, но не проверял вручную в самой игре UI привязки девоушенов —
   косвенное подтверждение через названия файлов и логику (телепорт/рывок —
   не "атаки", на которые вешаются проки).
5. **`points_cost`** = число узлов созвездия (эквивалентно очкам девоушена на
   его полное заполнение, так как в GD 1 узел = 1 очко) — это моя интерпретация
   поля, не отдельное явное поле в `.dbr`; проверил на нескольких созвездиях
   (Widow: 6 узлов = 6 очков, что совпадает с ожиданием из игры), но нет
   стопроцентной гарантии, что в исключительных случаях цена узла не равна 1
   очку (в игре везде так, отдельного поля "cost" на узле нет).
