## Как устроены цепочки лута (проверено на данных + подтверждено `field_schema.json`)

Коллега распаковал `database/templates.arc` и выложил `field_schema.json` — это
авторитетный словарь полей из редакторских шаблонов игры. Он **исправил одну мою
гипотезу** (см. ниже, самое важное) и подтвердил остальные три механизма.

```
LootMasterTable / LootItemTable_DynWeight   lootName{i} / lootWeight{i}
    -> взвешенный список: вероятность = lootWeight{i} / сумма ненулевых весов.
    lootName{i} может указывать И на предмет, И на ещё одну лут-таблицу
    (field_schema.json: lootName1 = "Item or LootTable") — резолвил рекурсивно
    по фактическому типу цели, а не по эвристике.

LevelTable                                  levels[] / records[]
    -> НЕ вероятность. field_schema.json: records = "Table to use when level is
    greater than or equal to the corresponding threshold level." Т.е. это выбор
    диапазона уровня персонажа/монстра: i-я запись работает для
    [levels[i], levels[i+1]-1], последняя — до бесконечности.

"fixeditemloot" (без Class)                 loot{N}Name{M}/loot{N}Weight{M}/loot{N}Chance[]
    -> несколько независимых "слотов" (loot1, loot2, ...), в каждом свой
    взвешенный список kaк у LootMasterTable. Используется FixedItemContainer.lootTable.
    loot{N}Chance — сырой массив из 10 чисел (‰?), под каким индексом какой смысл —
    НЕ разобрал (см. «Что не удалось»).

Monster                                     loot<Slot>ItemN / chanceToEquip<Slot>ItemN
                                             (+ отдельно chanceToEquip<Slot> без N)
    -> тот же паттерн "вес / сумма" на верхнем уровне: какая из N кандидат-таблиц
    слота используется. chanceToEquip<Slot> (без индекса) — отдельный "триггер-шанс"
    слота, в chance_hint НЕ входит (не знаю, как он на самом деле участвует в форму-
    ле шанса — не выдумываю).

FixedItemContainer                          lootTable
    -> список вариантов БЕЗ веса. field_schema.json прямым текстом называет то же
    самое поле levelOffset у шаблона lootcontainer "Normal, Epic, Ultimate" — то
    есть массив = по сложности, а НЕ взвешенные альтернативы.
```

### Важное исправление гипотезы (после field_schema.json)

**Первая версия скрипта ошибочно трактовала `loot<Slot>ItemN` (Monster),
`loot{N}Name{M}` (fixeditemloot) и `lootTable` (FixedItemContainer) как поля,
которые МОГУТ содержать список — и когда видела список, разворачивала его как
ДОПОЛНИТЕЛЬНЫЕ взвешенные альтернативы с тем же весом, что и у родительского
индекса.** Это было неверно и раздувало счётчики. `field_schema.json` прямо
говорит про эти поля: `class: array`, `description: "Index by game mode"` — то
есть элементы списка — это НЕ рандомные альтернативы, а разные версии предмета/
таблицы **для разных игровых сложностей** (судя по суффиксам файлов `n01b/e01/l01`
и по описанию `levelOffset` того же шаблона — "Normal, Epic, Ultimate"). Пофиксил:
теперь такие массивы разворачиваются как отдельный "difficulty"-хоп (не участвует
в `chance_hint`, вес относится к целому кандидату, а не к каждому элементу
массива). Без словаря полей я бы сдал скрипт с тихо неверными вероятностями —
это ровно тот случай, когда «сверься с гипотезой на 3+ записях» было бы
недостаточно (совпадения по 2-3 записям выглядели правдоподобно и без словаря).

## Схема `drop_sources.jsonl`

Одна строка — пара **(предмет, источник)**. Если один и тот же предмет достижим из
одного источника несколькими путями (разные слоты/сложности/ветки уровня), они
собраны в массив `variants` внутри одной строки (иначе файл распухал бы в разы без
новой информации — см. «Масштаб и вырезанное»).

```
item                 путь к .dbr предмета (лист цепочки)
item_name            резолв через tags.item_name() (itemNameTag/description/...)
item_is_mi           см. раздел "Monster Infrequent" ниже
source                путь к .dbr монстра/сундука
source_name           имя источника (тэг description монстра/сундука)
source_kind           "monster" | "chest"
variants[]            каждый элемент — один конкретный путь до предмета:
  slot                  какой слот монстра (Head/Chest/.../Misc1..3) или "lootTable[i]"/
                         "perPartyMemberDropItemName" у сундука
  path                  цепочка .dbr от источника до листа (rule 2 — сырьё для проверки)
  chain_kinds           тип каждого хопа: weighted | level | difficulty | fixed_guaranteed
  weight / weight_sum    вес листа и сумма весов внутри его непосредственного списка
  chance_hint            произведение (weight/weight_sum) ТОЛЬКО по хопам kind=weighted
                          вдоль всей цепочки. null, если в цепочке есть level/difficulty
                          хоп (это не вероятность, а жёсткий выбор) или сумма весов = 0.
                          НЕ включает chanceToEquip<Slot> (шанс, что слот вообще
                          сработает) — эту цифру не пересчитывал в вероятность,
                          см. «Честность» ниже.
  level_bracket          [min,max] диапазон уровня, если путь прошёл через LevelTable
  difficulty             "Normal"/"Epic"/"Ultimate"/строка-индекс, если путь прошёл
                          через "index by game mode" массив
variant_count          len(variants), для быстрой фильтрации "однозначных" дропов

# только для source_kind=monster:
slot_trigger_pct, monster_level_min/max, monster_classification,
is_hero/is_champion/is_boss/is_superboss/is_nemesis, faction

# только для source_kind=chest:
chest_classification, chest_level_min/max, chest_level_offset,
source_group_size (см. «Схлопывание сундуков»)
```

## Схема `loot_tables.json`

```
meta                        счётчики (см. «Счётчики» ниже)
weighted_tables_raw{}       ВСЕ LootMasterTable+LootItemTable_DynWeight как есть:
                            {table: [{"child":.., "weight":..}, ...]}
level_tables_raw{}          ВСЕ LevelTable как есть: {table: [{"level_min","level_max","child"}]}
fixeditemloot_raw{}         ВСЕ 523 "fixeditemloot"-узла как есть
monsters{}                  на каждого из 3735 монстров: имя/тэг, уровень (min/max +
                             сырая формула charLevel), классификация + is_* флаги,
                             faction (myFaction), gold_generator, slots{} (сырые
                             ссылки на кандидат-таблицы по каждому слоту, ДО раскрытия
                             в конкретные предметы — так покрыты и Common-монстры,
                             для которых в drop_sources.jsonl построчного разворота нет)
chests{}                    на каждый из 644 контейнеров: то же самое + lootTable
                             (варианты по сложности) + perPartyMemberDropItemName
chest_signature_groups[]    644 контейнера схлопываются в 129 уникальных наборов
                             lootTable-вариантов; тут — представитель + полный список
                             членов группы (см. ниже)
mi_items{}                  1625 предметов с флагом MI: имя, тип, item_level,
                             sources[] (все найденные источники, дедуплицированные)
```

## Monster Infrequent (MI) — как нашёл

Гипотеза: MI-предмет — это `.dbr`, у которого поле `modifierSkillName{N}` указывает на
файл в директории `.../skillmodifiers/monsterinfrequents/` (база+GDX1) или
`.../skillmodifiers/mi/` (GDX2/GDX3 переименовали папку). Проверил на многих
записях: 1625 предметов, 1624 из них с `itemClassification=Rare` (что совпадает с
тем, что в игре MI подсвечиваются как "rare"-тир). **Один исключение**:
`records/items/enemygear/restlessdeadlooter_sword2h.dbr` (`itemClassification=Common`,
`itemLevel=1`, `FileDescription="Wight"`) — это визуальное оружие НАЗ монстра
(вайта), лежит в папке `enemygear`, никогда не встречается ни в одной лут-таблице
(в `mi_items.sources` у него пусто) — считаю его ложным срабатыванием паттерна
путей (разработчики положили skill-модификатор в ту же папку для переиспользования),
но не выбросил из `mi_items` — просто у него `sources: []`, это видно.

Для КАЖДОГО из 1625 MI-предметов нашёлся хотя бы один источник (`MI items with NO
resolved drop source: 0`). Разбивка (см. `mi_items`, 1625 предметов):
- 192 — источники только монстры (специфичный дроп с конкретного героя/босса);
- 1433 — монстр(ы) **плюс** широкий пул бонусных/боссовых сундуков (см. ниже);
- 0 — только сундуки без единого монстра-источника.

### Почему у MI-предметов бывают сотни "источников"-сундуков

Часть боссовых/бонусных сундуков (`FixedItemContainer.lootTable` -> "fixeditemloot"
узел) содержит явные ссылки на `records/endlessdungeon/loottables/master/
mt_monsterinfrequents_{accessories,armor,weapons,weapons02}.dbr` — отдельные
мастер-таблицы, специально собирающие ЛЮБОЙ MI предмет соответствующей категории.
Это не баг резолвера — это реальная механика игры (бонусные "Trove"/"Coffer"/
"Reliquary" сундуки могут выдать любой MI, не только "свой"). Проверил на
`Kyzogg's Skull` (весовой фокус) — один явный монстр-источник ("Kyzogg the
Reanimator", `chance_hint=0.1` в его собственной таблице) + 123 сундука-дубликата
по всей игре после дедупликации (см. ниже) — это ожидаемо, не выдумано.

## Масштаб и что вырезано из drop_sources.jsonl (сознательно, честно)

Полное разворачивание "монстр × слот × кандидат-таблица × лист" для всех 3735
монстров и 644 сундуков без ограничений дало **десятки миллионов строк и >10 ГБ
оперативной памяти** при первом прогоне (убил процесс, не дав дописать файл — риск
для машины пользователя, у которой уже были проблемы с нехваткой RAM). Причина:
многие "слоты" (особенно Misc1/2/3 у монстров) ссылаются на ОБЩИЕ каталоги на
сотни-тысячи записей (`mt_hu_miscall_a01.dbr` -> 989 листьев, `..._c01` -> 3167),
переиспользуемые практически всеми монстрами игры — это не специфичный для
конкретного монстра дроп, а общий пул крафт-компонентов.

Что сделал (все пороги — константы в начале скрипта, легко поменять):
1. **`GENERIC_POOL_CAP = 60`** — если у конкретного слота/кандидата итоговый пул
   листьев больше 60, построчно НЕ разворачиваю (это "общий каталог", не
   специфика источника) — КРОМЕ MI-предметов, их ищу всегда, независимо от
   размера пула (отдельный проход `mi_subset()`, без полного сканирования).
2. **`NON_GEAR_ITEM_TYPES`** — типы-листья, которые технически являются частью
   лут-таблиц, но не "снаряжение, которое фармят": `ItemRelic` (89% строк на
   слотах Misc1-3 — это компоненты крафта), `ItemArtifactFormula`, `QuestItem`,
   `OneShot_Scroll`, `ItemNote`, `ItemFactionWarrant`, `ItemDifficultyUnlock`,
   `OneShot_SkillUnlock`, `OneShot_Food`. Исключены из общего среза (не для MI —
   MI такими не бывают по построению).
3. **Common-монстры** (742 из 3735, обычные трэш-мобы) — построчно НЕ разворачиваю
   не-MI предметы (их дроп — те же общие каталоги брони/оружия, что и у героев,
   ответ на них есть в `loot_tables.json.monsters[x].slots`, просто не расписан
   построчно). MI-дроп с обычных мобов ищется как обычно (0.28% строк файла — 326
   из ~118к — и это реально существующие в игре MI-от-обычного-моба случаи).
4. **Схлопывание сундуков**: 644 `FixedItemContainer` резолвятся всего в **129
   уникальных сигнатур** `lootTable`-вариантов (одна и та же таблица лута
   расставлена по десяткам похожих контейнеров в разных зонах — например у
   178 разных `secretchest_*.dbr` буквально идентичный `lootTable`). Считаю один
   раз на сигнатуру, `source` = представитель группы, полный список членов —
   в `loot_tables.json.chest_signature_groups` (и `source_group_size` в строке).
5. **Слияние (item, source)**: если к одной и той же паре ведёт несколько путей
   (разные слоты/сложности/ветки уровня), это ОДНА строка с массивом `variants`,
   а не N почти одинаковых строк (315 539 -> 175 878 после первого слияния,
   дальше упало до 117 871 после вырезания Misc-мусора).

Итог: 117 871 строк, 178.6 MB — тяжелее среднего среди задач пайплайна, но это
честный компромисс между полнотой (задание явно требует полный разбор MI и
цепочек боссов) и практичностью (без вырезания было бы ГБ мусора из компонентов
крафта). **Если требуется РОВНО "какая угодно броня с какого угодно моба" —
этого в drop_sources.jsonl нет построчно, но структура для восстановления есть**
(`loot_tables.json.monsters[x].slots` -> `weighted_tables_raw`/`level_tables_raw`).

## Честность про вероятности

`chance_hint` — это произведение `weight/weight_sum` **только** вдоль хопов вида
`weighted` в конкретном `variants[i]`. Он **не включает**:
- `chanceToEquip<Slot>` (шанс, что слот монстра вообще сработает при смерти) — не
  знаю точной формулы, как этот процент участвует в итоговом шансе (линейно? как
  вероятность независимого броска перед выбором таблицы?) — не пересчитываю,
  оставил сырым в `slot_trigger_pct`;
- множители сложности/уровня монстра/magic find — их нет в `.dbr` данных монстра
  вообще, это рантайм-механики движка;
- `loot{N}Chance` массив у "fixeditemloot" (10 чисел на слот) — не разобрал, для
  какого измерения (акт? версия игры? число игроков?) индексируется этот массив —
  оставил как сырой `chance_permille_raw` внутри `fixeditemloot_raw`, не
  использую для расчётов.

Там, где путь проходит через `LevelTable` или "index by game mode" (сложность),
`chance_hint = null` — это осознанный выбор, а не забытое поле: там нет
вероятности, там жёсткий выбор по условию (уровень/сложность), присвоить ему
число значило бы придумать несуществующий шанс.

## Что не удалось / в чём не уверен (обязательный раздел)

1. **`loot{N}Chance` (fixeditemloot, 523 узла)** — сырой массив из 10 чисел на
   каждый слот (`loot1Chance`, `loot2Chance`, ...). Не смог сопоставить индексы с
   конкретным контекстом (пробовал: акт/зона — не совпадает по количеству;
   сложность — не совпадает, сложностей 3-4, а чисел 10). Оставил как есть в
   `fixeditemloot_raw`, не использую.
2. **255-256 нерезолвленных ссылок** (`unresolved_child_refs_distinct`) — пути
   вроде `records/items/loottables/tdyn_waist_a01.dbr` (без суффикса версии),
   `lt_blueprints_d01_head.dbr` — встречаются в некоторых старых мастер-таблицах,
   но самих файлов в слитой `gd.sqlite` нет (видимо, переименованы/удалены в
   более позднем патче, а ссылающиеся мастер-таблицы не обновили). Такие ветки
   просто дают пустой список (не ломают резолв, я их не разворачиваю дальше и не
   выдумываю, чем они были).
3. **`chanceToEquip<Slot>` (общий процент слота)** — не знаю точно, как он
   сочетается с `chanceToEquip<Slot>ItemN` (выбор кандидата) в итоговую
   вероятность выпадения слота. Не пересчитываю, храню сырым.
4. **`is_nemesis`** — эвристика по пути записи (`/nemesis/` в имени `.dbr`) +
   есть отдельные "clone_*" квестовые враги с тэгом `tagNemesis_*`, которые НЕ
   попадают под эту эвристику (они не немезиды по сути, а декои одного квеста) —
   осознанно не включил их, но это значит что is_nemesis может быть неполным для
   каких-то редких квестовых сущностей.
5. **`faction` иногда = "UserNN"** (например у Каллагадры — `User16`) — это не
   баг извлечения: в `field_schema.json` `myFaction` буквально имеет такие
   значения в picklist (`User0`...`User40`) — часть фракций дополнений(ов) так и
   не получила читаемое имя в данных, значение честно взято из поля как есть.
6. **51 монстр без `monsterClassification`** — это не боевые монстры, а мирные
   NPC/стражники (`records/creatures/npcs/guard/...`), используют тот же шаблон
   `monster.tpl`, но поле не заполнено — ожидаемо, у них и лута обычно нет.
7. **241 монстр под `records/sandbox/...`** (тестовые/дев записи, вроде
   `boss_pemphredo_36.dbr`) — оставил в выдаче с флагом `is_sandbox=true`, не
   выбросил молча, но в игре их не встретить.
8. **6 циклов обнаружено и обрублено** (`cycles_detected`) — защита от
   зацикливания сработала 6 раз на реальных данных; не разбирал руками, какие
   именно таблицы циклятся (не критично — ветка просто даёт пустой список для
   этого захода, отмечено).
9. **Различие "Boss" vs "Champion" vs "Hero" в `monsterClassification`** — беру
   как есть из поля игры, не пытался домысливать "более специфичное" деление
   (например часть "Champion" визуально воспринимаются игроками как
   мини-боссы) — доверяю данным, а не игровым ощущениям.

## Спот-чек

**Босс → лут.** Каллагадра, Дитя Песков (`records/creatures/enemies/boss&quest/
sandscion_03.dbr`, `SuperBoss`) — слот `Misc1`, единственный кандидат
`tdyn_head_d201_scionsands.dbr` (`chanceToEquip=100%`), внутри — единственная запись
с весом 1000/1000. Итог: `item = gearhead/d220_head.dbr`, `item_name = "Callagadra's
Visage"`, `chance_hint = 1.0` (гарантированный дроп). Это совпадает с тем, что
известно про босса из игры — уникальный шлем, который она даёт гарантированно.

**MI-предмет → монстр.** `Bloodlord's Vengeance` (гуарда-меч, 5 вариантов по
`itemLevel`) — единственный источник во всех 5 вариантах: **Bloodlord Thalonis**
(герой), `chance_hint` от 0.09 до 0.13 в зависимости от варианта уровня предмета.
`Ragrathar's Horn` (фокус) — единственный источник **Ragrathar Rageblood**, тот же
паттерн. Оба героя и оба предмета реально существуют в игре именно в этой связке
(герой -> его уникальный MI) — совпадает с ожиданием.

**Сундук-группа.** 178 разных `secretchest_*.dbr` (уникальные "секретные" сундуки,
разбросанные по уровню) схлопнулись в одну сигнатуру `chestloot_all_secret(e/u)`.
Их пул — `mt_hu_miscall_c01/d01` (общие крафт-компоненты) + `mt_hu_miscrare_a01`
(редкая экипировка) — ни один MI не найден, что верно: секретные сундуки в игре
дают компоненты/случайную редкую вещь, а не гарантированный MI.

## Что вне области (не трогал — чужие задания/не запрошено)

- `LootRandomizerTable`/`LootRandomizer` (аффиксы) — только как ссылки внутри
  `LootItemTable_DynWeight` (`prefixTableName*`/`suffixTableName*`), не разворачивал —
  домен задания 11.
- `SetPiecePool`/`SetPiece` — по факту это система расстановки объектов по уровню
  (деревья, камни, breakable-ящики, **и** прокси немезид/сундуков), а не таблица
  весов лута. Для немезид there's ещё одна цепочка: `Monster` (немезида) не хранит
  прямой ссылки на свой сундук — связь идёт через `SetPiecePool -> Proxy ->
  ProxyAccessoryPool -> FixedItemContainer` (проверил на `nemesis_undead`: `set_
  nemesis_undead.dbr` -> `chestproxy_nemesis_undead.dbr` -> `pool_nemesis_undead0N.dbr`
  -> `n01_nemesischest_undead01.dbr`). Эти сундуки УЖЕ есть в `FixedItemContainer`
  (644 штуки, значит и в `chests_out`), просто их привязка к конкретной немезиде
  явно не восстановлена (`Proxy`/`ProxyAccessoryPool` — не в списке типов задания).
  Если это важно — отдельный маленький доп.-проход по этим двум типам.
- Точные координаты/локации монстров — не выдумывал, это `world001.map` (задание 31).

## Итог

- `data/grim-dawn/drop_sources.jsonl` — 178 627 129 байт, 117 871 строк
- `data/grim-dawn/loot_tables.json` — 54 311 506 байт
- 3735 монстров, 644 контейнера (-> 129 уникальных наборов лута), 1625 MI-предметов
  (все с хотя бы одним источником)
- Три главные неопределённости: (1) `loot{N}Chance` — не разобрал смысл индексов
  10-элементного массива; (2) `chanceToEquip<Slot>` — не знаю как сочетается с
  выбором конкретного кандидата в итоговую вероятность; (3) связка
  немезида-монстр -> её сундук идёт через `Proxy`/`ProxyAccessoryPool`, которые
  не разворачивал (вне заявленной области типов).
