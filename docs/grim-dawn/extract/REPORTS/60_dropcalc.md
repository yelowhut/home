# Отчёт 60 — Калькулятор шанса дропа

Скрипт: `docs/grim-dawn/extract/60_dropcalc.py`
Выход: `data/grim-dawn/drop_rates.jsonl` — 259 293 строк, 117 174 499 байт (117.2 MB)
Подкоманда: `python 90_query.py kills "<предмет>"` (добавлена в `90_query.py`, остальные
подкоманды не тронуты).

Запуск: `python 60_dropcalc.py` из `docs/grim-dawn/extract`, без аргументов. Отработал
без ошибок за ~2 минуты, полный лог валидаций смотрел вживую (см. ниже — это тот же
вывод, что печатает скрипт).

## Модель

Для каждой строки `drop_sources.jsonl` (пара предмет+источник, `variants[]` внутри)
и для каждой из трёх сложностей (`Normal`/`Epic`/`Ultimate`):

```
P(вариант) = (slot_trigger_pct/100, если source_kind=monster, иначе 1.0)
             x Пи по хопам kind=weighted (weight_i / weight_sum_i)
P(предмет за одно убийство/открытие | сложность) = 1 - Пи по подходящим вариантам (1 - P(вариант))
kills_X = ceil( ln(1-X) / ln(1-p) ),  X in {0.5, 0.9, 0.99}
```

**Почему нельзя было просто взять `chance_hint` из `drop_sources.jsonl`**: он посчитан
только для вариантов, где ВСЯ цепочка — сплошные `weighted`-хопы (11%, короткие цепочки).
Как только в цепочке есть `level`- или `difficulty`-хоп (88% вариантов), `chance_hint=null`
— и это осознанный выбор задания 30, не баг (см. `REPORTS/30_loot.md`). Хранится только
ОДНА пара `weight`/`weight_sum` на вариант (последнего weighted-хопа), веса промежуточных
звеньев в `drop_sources.jsonl` нет вообще.

**Как пройдено заново**: скрипт грузит `loot_tables.json` целиком в память (~150-200 MB
как python-объект, замерено `tracemalloc` до запуска — безопасно) и по `variant["path"]`
+ `variant["chain_kinds"]` (это ЕСТЬ в drop_sources.jsonl — сама структура цепочки, но не
веса) заново ищет вес каждого `weighted`-хопа:
- хоп 0 монстра (`source_kind=monster`, `table==source`) → `monsters[source].slots[slot].candidates`;
- `LootMasterTable`/`LootItemTable_DynWeight` → `weighted_tables_raw[table]`;
- `"fixeditemloot"`-узел → перебор его `loot{N}`-слотов в `fixeditemloot_raw[table]`
  (слот не всегда известен из строки заранее — ищем совпадение ребёнка).

Если следующий хоп — `difficulty` (список "index by game mode"), ищем ребёнка не в
`path[i+1]` (там повторно лежит имя того же узла — так устроен hop-формат задания 30),
а в `path[i+2]` (или в самом предмете, если хоп последний), и сверяем через
`x in val` (значение-список содержит искомый путь). `level`- и `difficulty`-хопы веса
не дают (это жёсткий выбор, не случайность) — они лишь определяют, какие варианты
вообще участвуют в сумме по выбранной сложности.

`drop_sources.jsonl` (170+ MB) читается потоково построчно, ни разу не грузится в
память целиком — это то самое место, где у автора задания 30 улетело 10 ГБ RAM,
здесь по построчному стриму риска нет (проверено: пиковая память не отслеживалась
формально, но структура кода гарантирует, что в памяти одновременно только:
`loot_tables.json` (~200 MB) + одна строка `drop_sources.jsonl` за раз + растущий
список выходных строк `drop_rates.jsonl`, который тоже можно было бы стримить на диск,
но 259k мелких dict'ов - не проблема для памяти).

## Схема `drop_rates.jsonl`

Одна строка = (предмет, источник, сложность). 259 293 строки (было 117 871 строк x
до 3 сложности - минус те комбинации, где сложность недостижима: `p=0` для этой
сложности не пишем вообще, строка просто отсутствует).

```
item, item_name            путь к .dbr предмета + резолвленное имя
source, source_name         путь к .dbr источника + имя (монстр или сундук)
source_kind                 "monster" | "chest"
difficulty                   "Normal" | "Epic" | "Ultimate"
monster_level_min/max        диапазон уровня ИСТОЧНИКА как есть в Monster-записи
                              (см. «Допущения» — у 79% монстров это буквально 1-250,
                              т.е. НЕ уровень конкретного убийства)
p_per_kill                   вероятность за одно убийство/открытие (см. формулу)
kills_50/90/99                число попыток для увер. 50%/90%/99%
variants_used                 сколько вариантов цепочки вошло в объединение
assumptions[]                 какие допущения применены именно к этой строке
                              (см. «Допущения», коды ниже)
```

## Обязательная валидация (все 4 — с цифрами)

### 1. Гарантированные дропы (p должен быть 1.0)

834 строки `drop_rates.jsonl` имеют `p_per_kill >= 0.999999`. Пример из задания —
Каллагадра → Callagadra's Visage:

```
source=records/creatures/enemies/boss&quest/sandscion_02.dbr  difficulty=Normal/Epic/Ultimate  p_per_kill=1.0  kills_50=kills_90=kills_99=1
source=records/creatures/enemies/boss&quest/sandscion_03.dbr  difficulty=Normal/Epic/Ultimate  p_per_kill=1.0  kills_50=kills_90=kills_99=1
```

(Два монстр-.dbr с одним и тем же именем "Callagadra, Scion of the Sands" — это НЕ
дубль/баг, а две разные записи, обе с весом 1000/1000 в единственном кандидате слота
`Misc1` — цепочка `("weighted",)` длиной 1.) Все 72 варианта `fixed_guaranteed`
и оба варианта Каллагадры дают `p=1.0` ровно — модель воспроизводит гарантированные
дропы **точно**, без округления и без "почти 1.0".

### 2. Сумма долей внутри таблицы ≈ 1.0 (10 случайных таблиц)

Проверено НЕ тавтологически (не сверка `loot_tables.json` самого с собой), а заново
по сырым полям `lootNameN`/`lootWeightN` в `gd.sqlite`:

| `tdyn_gun2hcrossbow_d101.dbr` | 14425 | 14425 | 1.0000 |
| `mt_gearweaponsranged_d01.dbr` | 1000 | 1000 | 1.0000 |
| `mt_geararmorhead_d03_witchgodguardian.dbr` | 1000 | 1000 | 1.0000 |
| `tdyn_gun2h_d101.dbr` (pets) | 19575 | 19575 | 1.0000 |
| `tdynx_enemy_blunt1h_broken.dbr` | 9600 | 9600 | 1.0000 |
| `tdyn_head_b03_outlawmurderer_common.dbr` | 3150 | 3150 | 1.0000 |
| `mt_setsdemo_01.dbr` | 100 | 100 | 1.0000 |
| `mt_gearweaponsmeleeblunt1h_c01.dbr` | 1000 | 1000 | 1.0000 |

Все 10/10 совпали с `gd.sqlite` (ratio 1.0000), и внутри каждой таблицы доли всех
элементов суммируются в 1.0000 — т.е. и извлечение задания 30, и наш пересчёт

### 3. Монотонность (p варианта ≤ slot_trigger_pct/100)

**0 нарушений из 238 105 вариантов.** Максимальный p одного варианта за весь
прогон: `1.000000` (единственный candidate 1000/1000 при 100% trigger — Каллагадра).

При первом прогоне здесь была найдена и исправлена реальная аномалия: у монстра
`records/creatures/enemies/boss&quest/bandit_oldwounds.dbr`, слот `LeftHand`,
`chanceToEquipLeftHand = 1000` (единственный случай во всей игре — все остальные
`trigger_pct` в данных ≤100, см. распределение: 4085 записей = 100.0, дальше 30.0,
0.0, 15.0...). Без клэмпа это давало `p_variant = 10.0` — абсурд, поймали именно
валидацией 3/4, а не поверили сырым цифрам. Зафиксировано как явный выброс
авторских данных, значение клэмпится к 100% (тег `trigger_pct_clamped_100`,
встречается у 3 строк — 1 монстр x 3 сложности).

### 4. Здравый смысл (3 известных MI-предмета)

| Предмет | Источник | p за убийство | kills_50 / 90 / 99 |
|---|---|---|---|
| Kyzogg's Skull (вариант b025a) | Kyzogg the Reanimator | 20.0% | 4 / 11 / 21 |
| Kyzogg's Skull (вариант b025b) | Kyzogg the Reanimator | 16.0% | 4 / 14 / 27 |
| Bloodlord's Vengeance | Bloodlord Thalonis | 12.8% | 6 / 17 / 34 |
| Ragrathar's Horn | Ragrathar Rageblood | 25.6% | 3 / 8 / 16 |

Все три — единственный конкретный герой-источник (`variants_used=1`, слот

реальные разные `itemLevel`-версии одного MI (как и `Bloodlord's Vengeance` в
отчёте задания 30, у которого было 5 таких вариантов).

## Допущения (честно, по кодам в `assumptions[]`)

| Код | строк с этим тегом | что значит |
|---|---|---|
| `level_gate_summed` | 180 933 / 259 293 (70%) | цепочка проходит через `LevelTable`; у 79% монстров `minLevel/maxLevel` в данных — буквально `1/250` (движок масштабирует уровень монстра под игрока), т.е. НЕТ данных о том, на каком именно уровне произойдёт конкретное убийство. Модель суммирует ВСЕ ветки `LevelTable`, подходящие по сложности, через ту же union-формулу `1-Пи(1-p)` — это ЗАВЫШАЕТ p, если игрок фармит монстра на одном фиксированном уровне (тогда реально доступна только ОДНА ветка, а не все). Для боссов с узким диапазоном уровня (99 из ~249 по ширине, редко) эффект слабее. |
| `chest_trigger_assumed_100` | 128 907 / 259 293 (50%) | у сундуков нет аналога `chanceToEquip<Slot>` монстра — считаем, что открытие сундука ВСЕГДА генерирует лут этого слота (не проверено, в `.dbr` данных такого поля просто нет). |
| `excluded_unknown_difficulty_index` | 47 142 строк-исключений (соответствуют 47 592 вариантам) | обнаружен 4-й "index by game mode" (метка `"3"`) — ТОЛЬКО у сундуков (`FixedItemContainer.lootTable` с 4 элементами вместо 3, напр. `chest_bossloot_03/03e/03u/03a.dbr`, `levelOffset=[3,4,5,5]`). Судя по данным (Normal/Epic/Ultimate иногда буквально ОДНА И ТА ЖЕ таблица, а 4-й слот — ОТДЕЛЬНАЯ, ведущая в `mt_monsterinfrequents_*`), это похоже на отдельный "бонус-MI ролл", а не 4-ю сложность — но это ДОГАДКА, не подтверждено полем `field_schema.json` (там `levelOffset` описан только как "Normal, Epic, Ultimate", 3 значения). Не выдумываю смысл — такие варианты просто НЕ включены в Normal/Epic/Ultimate расчёт (т.е. p_per_kill для этих сундуков может быть НЕДООЦЕНЕН, если 4-й слот реально стакается поверх обычного лута). |
| `trigger_pct_missing_assumed_100` | 393 | у слота монстра нет поля `chanceToEquip<Slot>` вообще — считаем 100%. |
| `trigger_pct_clamped_100` | 3 (1 монстр x 3 сложности) | `chanceToEquipLeftHand=1000` у `bandit_oldwounds.dbr` — явный выброс данных, клэмп к 100%. |

Плюс — общие допущения, которые тегами по строкам не размечены (действуют
на ВСЕ строки одинаково, перечислены в `TASKS/60_dropcalc.md` как заведомо
неизвестное):
1. **Независимость слотов** — слоты одного монстра/сундука (Head, Chest, Misc1...)
   считаются независимыми бросками. Не проверено в данных, не опровергнуто.
2. **Magic Find / "% Item Rarity"** — нет в `.dbr`, это чисто рантайм-механика
   движка. Не моделируется вообще — реальный шанс в игре ВЫШЕ посчитанного здесь.
3. **Множители дропа по сложности сверх выбора таблицы** — не найдены в данных
   (в отличие от `mechanics.json.from_db.difficulty_monster_scaling`, который
   относится к масштабированию СТАТОВ монстра, не к луту — не использовал его
   для дропа, это была бы неподтверждённая экстраполяция).
4. **Число игроков в отряде** — есть ось "игроков" в некоторых `raw`-массивах
   механик (см. `TASKS/60_dropcalc.md`), но связь с лутом не подтверждена и не
   использована.
5. **Объединение вариантов через `1-Пи(1-p)`** — это буквально формула из задания,
   но она технически ПРЕДПОЛАГАЕТ независимость вариантов. Если бы 2 разных
   элемента ОДНОГО weighted-списка вели к одному и тому же предмету (мы такого
   не встретили явно в 3 живых примерах, но не проверяли ВСЕ 259k строк на этот
   счёт), формула слегка завысила бы p против точного «сумма весов / weight_sum»
   для взаимоисключающих альтернатив одного броска. Разница пренебрежимо мала при
   малых p (что и есть почти везде), с точностью до долей процента.

## Что это значит для точности числа "убийств"

Из-за `level_gate_summed` (70% строк) и `chest_trigger_assumed_100` (50% строк)
**итоговое `kills_50/90/99` — это, честно говоря, ОРИЕНТИР, а не точное число**:
для монстров с широким диапазоном уровня оно, вероятнее всего, НИЖЕ реального
(модель суммирует более широкий пул шансов, чем реально доступен на одном уровне
персонажа), а для 4-й ветки сундуков (`excluded_unknown_difficulty_index`) —
наоборот, могло быть НЕДООЦЕНЕНО (бонус-ролл, если он есть, не учтён). Где
`variants_used=1` и `assumptions=[]` (простые одноисточниковые MI, как в
валидации 4) — числа точнее всего. Где `assumptions` не пуст — читайте их
как «от X до большего», не как факт.

## Что не удалось / в чём не уверен

1. **4-й "index by game mode" у сундуков (см. `excluded_unknown_difficulty_index`)**
   — не понял его точный игровой смысл (бонус-MI-ролл? отдельный "endless dungeon"
   режим? судя по пути `records/endlessdungeon/...` внутри — вероятно второе, но
   не проверял отдельно игровые патчноуты/wiki, только по данным). Не подставил
   в Normal/Epic/Ultimate, чтобы не соврать; 47 592 варианта честно выброшены.
2. **Уровень монстра на конкретном убийстве** — ключевое ограничение всей модели
   (см. `level_gate_summed`). У подавляющего большинства монстров `minLevel=1,
   maxLevel=250` в данных, это диапазон ВСЕЙ игры, а не диапазон конкретной
   встречи. Без данных о фактическом распределении уровней монстра на карте
   (`world001.map`, вне области этого задания) точнее посчитать нельзя.
3. **Есть ли реальный "trigger" у сундуков** (аналог `chanceToEquip<Slot>` монстра)
   — в `.dbr` полях `FixedItemContainer` такого поля нет вообще, допущение 100%
   не проверено против игрового опыта.
4. **Независимость слотов монстра** — стандартное допущение калькуляторов дропа
   для этой игры, но не подтверждено данными `.dbr` (это рантайм-логика движка).
5. **Единственный выброс `chanceToEquipLeftHand=1000`** (bandit_oldwounds.dbr) —
   клэмпнут к 100% без уверенности, что это правильная интерпретация (могло
   быть намеренным 10x-множителем в другой единице измерения — не подтверждено).
