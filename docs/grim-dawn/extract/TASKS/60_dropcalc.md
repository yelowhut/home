# Задание 60 — Калькулятор шанса дропа

Скрипт: `60_dropcalc.py` → `data/grim-dawn/drop_rates.jsonl`
Отчёт: `REPORTS/60_dropcalc.md`

## Цель

Ответить на вопрос игрока: **«сколько раз убить этого монстра, чтобы выбить этот предмет?»**
Сейчас данные о дропе есть, но вероятность по цепочке не свёрнута.

## Что уже установлено (не перепроверяй, используй)

Задание 30 извлекло `drop_sources.jsonl` (117 871 строка) и `loot_tables.json`. Замеры:

- Вариантов дропа всего 238 105, из них `chance_hint` посчитан лишь у **27 157 (11%)** —
  только для коротких цепочек. У 88% цепочка из 5 звеньев, и там `chance_hint = None`.
- Типы звеньев цепочки: `weighted` (686 746), `level` (209 400), `difficulty` (177 588),
  `fixed_guaranteed` (72).
- Значения сложности в данных: `Normal`, `Epic`, `Ultimate` (**`Epic` = внутриигровое
  имя сложности Elite**), плюс встречается числовой индекс.
- `level_bracket` вида `[1, 11]`, `[1, 17]` — гейт по уровню.
- В `mechanics.json → from_db.difficulty_monster_scaling` массивы `raw` по 12 элементов =
  **3 сложности × 4 количества игроков** (индекс = difficulty*4 + players-1). Эту раскладку
  подтверди на данных, прежде чем использовать.

**ВАЖНО**: в `drop_sources.jsonl` хранится только ОДНА пара `weight`/`weight_sum` на вариант,
а не веса каждого звена. Поэтому цепочку придётся **пройти заново** по `loot_tables.json`
и/или `gd.sqlite`, а не постобрабатывать `drop_sources.jsonl`.

## Что посчитать

Для связки «предмет × источник × сложность»:

```
P(вариант) = slot_trigger_pct/100 × Π по всем weighted-звеньям (weight_i / weight_sum_i)
             при условии, что difficulty-звенья соответствуют выбранной сложности,
             а level-звенья пропускают предмет на данном уровне монстра
P(предмет за убийство) = 1 − Π по всем вариантам (1 − P(вариант))
```

Число убийств для уверенности X: `n = ln(1−X) / ln(1−p)`. Выдай для X = 50%, 90%, 99%.

## Выход

`drop_rates.jsonl`, по строке на «предмет × источник × сложность»:
`{item, item_name, source, source_name, difficulty, monster_level_min/max,
  p_per_kill, kills_50, kills_90, kills_99, variants_used, assumptions: [...]}`

Плюс подкоманда в `90_query.py`: `python 90_query.py kills "<предмет>"` — выводит
источники и число убийств по сложностям. **Меняй только свою подкоманду**, остальной
файл не трогай.

## Обязательная валидация (иначе задание не принято)

1. **Гарантированные дропы.** 72 звена `fixed_guaranteed` и известный случай
   Callagadra → «Callagadra's Visage» (вес 1000 из 1000) должны дать `p = 1.0`.
   Если не дают — модель неверна.
2. **Сумма по таблице.** Для любой одной `weighted`-таблицы сумма долей всех её
   элементов должна быть ≈ 1.0. Проверь на 10 случайных таблицах, приведи цифры.
3. **Монотонность.** `p` не должен превышать `slot_trigger_pct/100`.
4. **Здравый смысл.** Возьми 3 известных MI-предмета и посмотри, не получаются ли
   абсурдные числа (миллионы убийств или 100% на всё). Абсурд = ошибка в модели.

## Честность важнее красоты числа

Раздели выход на посчитанное и предположенное. Перечисли в `assumptions` и в отчёте всё,
что ты **допустил**, а не вывел из данных. Заведомо неизвестное (не выдумывай):

- независимо ли роллятся разные слоты лута одного монстра;
- как влияет игровой стат «% Item Rarity» (magic find);
- есть ли глобальные множители дропа по сложности сверх выбора таблицы;
- влияет ли количество игроков (в `raw`-массивах ось игроков есть, но связана ли она с лутом).

Если после честного учёта неизвестных итоговое число нельзя назвать точным — так и напиши,
и подай его как **нижнюю/верхнюю оценку или относительный ориентир**, а не как факт.
Лучше «от 40 до 200 убийств, потому что неизвестен множитель X», чем уверенные «73».
