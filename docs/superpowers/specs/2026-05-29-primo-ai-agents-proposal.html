Раздел 01

Что такое ИИ агенты и зачем они нужны

Primo AI Server сегодня умеет распознавать документы (Умный OCR) и обрабатывать текст (AI Text). Следующий шаг — ИИ агенты, которые не просто обрабатывают данные, а доводят результат до целевых систем.

ИИ агент в контексте Primo RPA

ИИ агент — это программа, которая получает задачу на естественном языке, сама определяет шаги для её решения, обращается к корпоративным системам (1С, почта, документы) и возвращает результат. В отличие от RPA-робота, агент понимает текст и принимает решения. В отличие от чат-бота, агент действует — не просто отвечает, а выполняет операции в системах.

Чат-бот
Отвечает на вопросы. Не действует в системах. Нет доступа к корпоративным данным.
ИИ агент
Понимает задачу, рассуждает, действует в системах. Запрашивает подтверждение на критичные операции.
RPA-робот
Выполняет строго заданный алгоритм. Не понимает текст. Не адаптируется к исключениям.

Три типа исполнителей

Каждый подходит для своего класса задач. Выбор определяется балансом между предсказуемостью и гибкостью.

Что блокирует AI-сервер сегодня — и роль агента

В стратегической документации зафиксированы 4 основных кейса, которые AI-сервер в текущем виде не закрывает. Их объединяет общий разрыв: AI-сервер умеет обработать документ (OCR, классификация, извлечение данных), но не умеет дальше довести результат до смежных систем (1С, ERP, почта, файловые хранилища). Именно это «доведение результата до целевой системы» и есть задача AI-агента.

Единственный реальный блокер — отсутствие MCP к AI-серверу

Сам агент и языковая модель для PoC могут быть практически любыми — это не блокер. Для проверки гипотезы достаточно внешнего агента и внешней модели (Claude).

Пока AI-сервер (OCR, NLP, выдача обработанных документов) не выставлен наружу как MCP, агенту не на что опираться. Поэтому разработка MCP к AI-серверу выносится в нулевую фазу роадмепа.

Конкретные бизнес-сценарии

Сценарный агент

Обработка входящего счёта

Агент получает счёт по email, распознаёт реквизиты через OCR, сверяет с данными контрагента в 1С, при совпадении — проводит документ. При расхождении — запрашивает подтверждение оператора.

Сценарный агент

Ответ на запрос ФНС

Агент получает запрос, классифицирует тип, находит нужные документы в корпоративной базе знаний (RAG), формирует ответ со ссылками на источники, отправляет на согласование юристу.

Автономный агент

Разбор исключения по счёту

Застрявший в обработке счёт. Агент сам решает, куда смотреть: лезет в 1С за историей контрагента, проверяет условия договора, сравнивает позиции, формулирует причину расхождения и предлагает решение.

Длинный процесс

AI-онбординг сотрудника

Шаги растянуты на весь испытательный срок — дни, недели, месяцы. Процесс приостанавливается и возобновляется спустя произвольное время. Канонический пример, требующий durable-execution (см. раздел 03).

Почему нужны оба типа агентов?

Сценарные агенты покрывают 70-80% задач — типовые процессы с известным маршрутом. Но оставшиеся 20-30% — исключения, аналитика, нестандартные запросы — требуют агента, который умеет рассуждать. Без автономных агентов мы проигрываем конкурентам на сложных кейсах. Без сценарных — не закрываем массовый enterprise-спрос.

Архитектурно оба типа — это разные стратегии исполнения поверх единой платформы. MCP-серверы, LLM Provider, Governance, UI — общие. Разница только в движке выбора следующего шага.

Поток данных: от запроса до результата

Единый поток AgentEvent — thought, tool_call, tool_result, approval_request, answer. UI, логирование и governance работают одинаково для обоих типов.

Поток данных: автономный агент обрабатывает запрос пользователя. Для сценарного агента вместо цикла THINK/ACT/OBSERVE идёт последовательность заданных шагов — EventStream и UI одинаковые

Автономный агент: ReAct-цикл

LLM сам выбирает, какой инструмент вызвать и когда остановиться. Цикл Think → Act → Observe повторяется до решения задачи или исчерпания лимитов.

Раздел 03

Хранение состояний между шагами — ключевая сложность

По итогам обсуждения это самая тяжёлая часть сценарного агента — возможно, более сложная, чем кажется сейчас. От выбора здесь зависит вся архитектура runtime.

Почему состояние нужно хранить

Шаги агента — не одна непрерывная транзакция. Между ними возможны:

  • • Human-in-the-loop — процесс ждёт решения человека (минуты, часы).
  • • Длинные фазы ожидания — дни, недели, месяцы (AI-онбординг сотрудника).

Процесс должен уметь приостанавливаться и возобновляться спустя произвольное время, переживая рестарты сервиса. Это задача durable-execution, а не «сохранить контекст диалога».

Почему PostgreSQL «в лоб» — плохая практика

Соблазн хранить состояние как строки/JSON в Postgres велик, но у нас неопределённость в том, какие процессы будут и какие состояния нужно хранить.

Проектировать жёсткую схему под неизвестные процессы — значит почти гарантированно её ломать и мигрировать. Нужен слой, управляющий состоянием и переходами как первоклассной сущностью, а не самописная машина состояний поверх таблиц.

Риск, который фиксируем прямо: «упороться» в Celery

Направление — очередь задач / durable-execution. Базовый кандидат — Celery или более верхнеуровневые инструменты на его базе: отложенные задачи, ретраи, расписания закрывают «ожидания» и частично HITL.

У Celery есть глобальная проблема — сложность. Использовать его «в сыром виде» под долгоживущие приостанавливаемые процессы — это риск написать поверх него самодельный движок состояний и утонуть в нём. Поэтому:

либо берём обёртку/оркестратор поверх Celery, скрывающую сложность;
либо отдельно оцениваем purpose-built durable-execution движки (где приостановка/возобновление — встроенная функция).
Главное решение раздела: состояние и долгоживущие процессы строим на готовом движке, а не пишем с нуля поверх PostgreSQL. Конкретный выбор (Celery-обёртка vs purpose-built) — развилка №3 для техдира, решить до Фазы 2.
Раздел 04

MCP-серверы и интеграции

Агент общается с интеграциями по протоколу MCP. Добавление новой интеграции = новый MCP-сервер в MCP Router. Каждый требует предметной экспертизы в своей области.

MCP к AI-серверуДоступ к OCR/NLP/выдаче обработанных документов AI-сервера. Критический блокер всего продукта.Фаза 0
1С (REST/OData)Чтение справочников, документов, контрагентов. Создание/проведение документов. Загрузка обработанных документов.PoC / MVP

Почему MCP к AI-серверу — нулевая фаза: все 4 нерешённых кейса упираются в одно — обработанный AI-сервером документ нужно довести до целевой системы, а для этого агенту нужен программный доступ к AI-серверу через MCP. Пока этого MCP нет, любой агент (хоть Claude, хоть собственный) бесполезен. Поэтому он идёт раньше всего остального.

Контракт MCP-сервера

Агент не знает деталей реализации интеграции — он вызывает инструмент MCP-сервера по имени. MCP Router маршрутизирует вызов в нужный сервер. Это даёт совместимость со стандартом и позволяет переиспользовать чужие MCP-серверы.

MCP Tool (в составе MCP-сервера): name: str # уникальный идентификатор description: str # описание для LLM parameters: JSONSchema # входные параметры requires_approval: bool # нужно ли подтверждение оператора invoke(params) → Result # вызов через MCP (sync / async)

Интеграция с 1С (OData)

1С 8.x публикует OData-интерфейс из коробки. Агент не знает про OData — вызывает инструмент MCP-сервера по имени с параметрами, сервер транслирует в запрос.

Доступные операции
find_partner, get_invoice, create_document, post_document, list_registers
Требования к заказчику
1С 8.x с включённым OData, сетевой доступ от сервера агентов до 1С

RAG — поиск по документам с цитированием

Enterprise-требование: ответ должен содержать ссылку на конкретный источник (документ, страницу).

MCP к AI-серверу (нулевая фаза)

OCR
Распознавание документов и сканов. Агент отправляет файл, получает структурированный текст с координатами полей.
NLP
Классификация текста, извлечение сущностей. Агент использует для автоматической маршрутизации документов по типу.
Выдача документов
Получение обработанных документов AI-сервера для дальнейшего доведения до целевых систем.

AI-сервер также остаётся production-провайдером LLM inference через абстракцию LLM Provider (раздел 05) — но это отдельный путь от MCP-доступа к OCR/NLP.

RPA-роботы как MCP-сервер

Post-MVP

Для систем без API агент может запустить RPA-робота через MCP. Робот выполняет действия в UI, агент получает результат.

Раздел 05

LLM Provider — абстракция над моделями

Переключение провайдера — одна строка в конфиге. Код агента не меняется. Это механизм перехода с Claude (PoC) на собственную модель.

LLM Provider: единый интерфейс. Claude на PoC, AI Server / Ollama / vLLM в проде, собственная модель — цель
llm: provider: claude # claude | ai_server | ollama | vllm | own model: claude-opus-4-x # на PoC embedding: provider: ollama model: bge-m3

Целевое состояние: собственные агент и модель

На PoC и агент, и модель — внешние (Claude). Это сознательный временный выбор ради скорости. В дальнейшем и агент, и языковые модели должны стать собственными. Архитектура заложена так, чтобы этот переход не требовал переписывания.

СлойPoCЦель
Агент (логика рассуждения/сценария)Claude Agent SDKСобственный Agent Runtime
Языковая модельClaudeСобственная (AI Server / vLLM)
Точка подмены—LLM Provider + MCP Router
Что это значит на практике: бизнес-логика, сценарии, MCP-серверы и governance не зависят от того, кто внутри — Claude или собственная модель. Миграция = смена провайдера в конфиге + перенос логики агента в собственный runtime, без затрагивания интеграций. Риск миграции и зависимость от Claude на переходный период вынесены в раздел «Риски».
Раздел 06

Governance — контроль и безопасность

Сквозной слой для обоих типов агентов. Без RBAC, аудита и guardrails enterprise-заказчик не пустит агента в контур.

RBAC — управление доступом

Интеграция с AD/LDAP/Keycloak. Разграничение: кто пользуется, кто настраивает, какие MCP-серверы доступны.

Audit Log — полная трассировка

{ "timestamp": "...", "session_id": "ses_abc123", "agent_id": "invoice-processor", "user_id": "operator@company.ru", "event": "tool_call", "tool": "1c.post_document", "params": { "doc_id": "INV-2024-001" }, "reasoning": "Счёт сверен, расхождений нет", "result": "success", "approved_by": "operator@company.ru" }

Каждое действие агента записывается: от запроса до финального результата. Для автономных агентов — полная цепочка рассуждений.

RBAC и audit — это не «потом», это условие первого пилота. MVP: базовые лимиты (макс. шагов, таймаут); полные guardrails — следующая фаза.
Раздел 07

Два варианта MVP

Общая архитектура, стек и подходы не меняются. Вариант MVP определяет только, какой тип агента строим первым.

Вариант A
Сценарные агенты
Цель Ц1-2 · Run
  • ✓ Предсказуемость демо
  • ✓ Высокое доверие enterprise
  • ✓ Ближе к продаже
  • ✗ Сложнее MVP (DSL графов)
  • ✗ Слабая дифференциация
  • ✗ Острее упирается в хранение состояний (раздел 03)

Демо-сценарий

«Обработка входящего счёта» — агент получает счёт, извлекает реквизиты через OCR, сверяет с 1С, при расхождении запрашивает подтверждение, проводит документ.

Календарь (3-4 недели)

Нед 1: LLM Provider, MCP-интерфейс, API Gateway, Chat UI
Нед 1-2: Scenario Executor (DSL, граф, переходы)
Нед 2-3: MCP-серверы (1С, Email), RAG
Нед 3-4: Audit log, human approval, стабилизация
Риск: DSL графов с ветвлениями — 2-3 недели. Плюс длинные ожидания и HITL требуют durable-execution (раздел 03), а не таблицы в Postgres.
Вариант B
Автономные агенты
Цель Ц1-3 · Discovery
  • ✓ Быстрее до MVP
  • ✓ Высокий wow-фактор на демо
  • ✓ Сильная дифференциация
  • ✓ Проще путь ко 2-му типу
  • ✗ Зависимость от качества LLM
  • ✗ Нужен human-in-the-loop

Демо-сценарий

«Разбор исключения по счёту» — агент получает застрявший счёт, сам решает куда смотреть, проверяет историю в 1С, условия договора, формулирует причину и предлагает решение.

Календарь (3-4 недели)

Нед 1: LLM Provider, MCP-интерфейс, API Gateway, Chat UI
Нед 1-2: Autonomous Executor (ReAct, tool calling)
Нед 2-3: MCP-серверы (1С, Email), RAG
Нед 3: Human-in-the-loop, audit с reasoning trace
Нед 4: Guardrails, стабилизация
Риск: ReAct-цикл проще (1-1.5 недели). Основной риск — качество LLM. Митигация: Claude на PoC/демо, локальную модель проверять отдельно.

Раздел 08

Фазы развития до конца 2026

Роадмеп пересобран по итогам встречи: впереди появляются нулевая фаза (MCP к AI-серверу) и десктопное приложение, после которых идёт прежнее тело роадмепа с адаптациями. Это снимает главный блокер до того, как вкладываться в остальное.

Сроки: добавление двух фронтальных фаз сдвигает прежнюю датировку (июнь→декабрь). Конкретные даты фиксируем после оценки Фазы 0, т.к. она на критическом пути и зависит от готовности AI-сервера к выставлению MCP.
Фаза 0 (нулевая) · MCP + PoC
MCP к AI-серверу + PoC
3-4 недели · критический путь · Discovery → Run
  • MCP к AI-серверу (OCR/NLP/выдача обработанных документов)
  • Связка PoC: AI-сервер + MCP + Claude как агент + Claude как модель
  • Один сквозной кейс: обработанный документ доведён до целевой системы
  • MCP к одной целевой системе (1С / почта) для «доведения результата»
  • Базовый audit log
Проверяем: работает ли связка «AI-сервер → MCP → агент → целевая система»? Закрывает ли хотя бы один из 4 нерешённых кейсов?
Фаза 1 · Десктоп
Десктопное приложение (чат на рабочем месте)
3-4 недели · первый рабочий клиент · Run
  • Десктоп-клиент (Electron/Tauri + чат-UI)
  • Чат с агентом, трейс шагов/рассуждений
  • Работа поверх связки Фазы 0 (MCP + Claude)
  • Human-in-the-loop в интерфейсе
  • Локальная установка на рабочем месте
Проверяем: можно ли показать заказчику ценность на его рабочем месте и получить интерес к пилоту? Основной артефакт для пресейлов.
Фаза 2 · Пилот + 2-й тип
Первый пилот + второй тип агента
Тело роадмепа, адаптировано · Discovery → Run
  • Второй тип агента
  • Durable-execution для длинных/HITL-процессов (Celery-based или purpose-built, раздел 03)
  • Проверка на локальных LLM (AI Server, Ollama) — шаг к собственной модели
  • RBAC: admin / operator / viewer; SSO: AD/LDAP

  • Мониторинг: дашборд работы агентов

Масштабирование, оркестрация, замена Claude

Раздел 09

Развилки для решения

7 решений, которые нужно принять до начала разработки. Для каждого — варианты, trade-offs и рекомендация.

1
MVP: сценарный или автономный?
A — Сценарный

Предсказуемо, ближе к продаже. Цель Ц1-2 (Run). Выше сложность MVP из-за DSL графов.

B — Автономный

Быстрее до MVP, сильнее на демо. Цель Ц1-3 (Discovery). Риск в качестве LLM.

▶ Рекомендация: Вариант B — проще, быстрее, легче путь ко 2-му типу. Решение за командой
2
Фреймворк агентов
Claude Agent SDK

Быстрый PoC, готовый агент + сильная модель, нативный MCP. Внешняя зависимость.

Кастомный runtime / LangGraph

Контроль и путь к собственному агенту. Дольше до результата либо vendor lock.

▶ Рекомендация: Claude на PoC, собственное — далее (раздел 05)
3
Движок состояний (раздел 03)
Celery (или обёртка над ним)

Уже распространён, отложенные задачи, ретраи. Риск самописного движка состояний.

Purpose-built durable-execution

Приостановка/возобновление процесса — встроенная функция, а не дописываем сами.

▶ Решить до Фазы 2; не писать с нуля поверх Postgres
4
Отношение к AI Server
Модуль внутри AI Server

Общий UI, auth, инфраструктура. Зависимость от релизного цикла AI Server.

Standalone продукт

Свой деплой, MCP-интеграция с AI Server. Независимость, но дублирование инфры.

▶ Обсудить с техдиром — стратегическое решение
5
Agent Builder
Строим сами

Полный контроль UX, оптимизация под наши сценарии. Дополнительное время разработки.

Переиспользуем из AI Server

Быстрее, но завязка на существующий UI/UX. Зависит от развилки №4.

▶ Зависит от решения по развилке №4
6
Vector Store
pgvector (PostgreSQL)

Уже в стеке, одна БД для всего. Достаточно для MVP и средних объёмов документов.

Qdrant

Быстрее на больших объёмах, ANN-индексы. Дополнительный компонент в деплое.

▶ Рекомендация: pgvector на старте — уже в стеке, минимум сложности
7
Протокол инструментов РЕШЕНО
Свой протокол

Полный контроль, оптимизация под наши нужды. Несовместимость с экосистемой.

MCP (Model Context Protocol)

Стандарт, совместимость с экосистемой, переиспользование чужих MCP-серверов.

▶ Решено: MCP — все коннекторы суть MCP-серверы (разделы 01, 04)
