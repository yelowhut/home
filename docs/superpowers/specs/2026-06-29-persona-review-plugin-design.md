# Дизайн: плагин `persona` — ревью документа от лица недружественной внешней аудитории

Дата: 2026-06-29
Статус: реализован, влит в main, проверен e2e на реальном документе (2026-06-30)

Синхронизация 2026-06-30 (по итогам боевого прогона): добавлены вопрос об аудитории/цели
(фаза 4, первым), извлечение текста для больших/HTML входов (фаза 2), протокол прогресса и
фиксация Opus в фазе 6, обязательный UTF-8-заголовок в HTML-отчётах (§8).

## 1. Назначение

Плагин Claude Code `persona` запускается командой `/persona:review` и проводит аналитику
документа (или папки документов) **от лица внешней, недружественной аудитории**. Каждая
персона — внешний человек со своими интересами, который по умолчанию **не на стороне автора**.

Универсальность обязательна: вход может быть чем угодно — ТЗ, политика ИБ, договор,
маркетинговый текст, регламент. Пайплайн определяет тип документа сам и адаптирует роли.

Итог — структурированная обратная связь от каждой персоны и сводный отчёт, пригодный для
скармливания другим пайплайнам, улучшающим качество документов.

## 2. Принципы

- **Внешняя нелояльность.** Персоны никогда не считают пользователя частью своей команды.
  У них свои KPI, своя компания, свои риски. Документ для них — потенциальная угроза/издержка,
  пока не доказано обратное.
- **Повторяемость.** Три запуска с одними параметрами дают максимально схожий результат.
  Держится на трёх рычагах: кэш персон по ключу, структурный (не свободнотекстовый) ввод
  параметров, жёсткие JSON-схемы вывода ревьюеров и синтеза. Temperature на Opus в Claude Code
  напрямую не управляется — на неё НЕ опираемся.
- **Переносимость.** Самодостаточный плагин; копируется/устанавливается в любой репозиторий.
- **Профессиональный язык.** Без формальностей и канцелярита.
- **Локальность промежуточных данных.** Все черновики и размышления — на диск в рабочий
  каталог, пока пайплайн не завершён. Ничего важного не держим только в эфемерном контексте.

## 3. Форма поставки — плагин `persona`

```
persona/
  .claude-plugin/plugin.json          # манифест плагина
  commands/
    review.md                         # /persona:review — точка входа, оркестратор
  skills/
    persona-review/
      SKILL.md                        # логика пайплайна (фазы 1-8)
      references/
        document-analysis.md          # анализ входа: тип документа, язык, аудитория, тезисы
        persona-archetypes.md         # таблицы архетипов: секторы, роли, имена, компании
        reviewer-protocol.md          # рубрикатор отзыва + 5 уровней враждебности (поведение)
        synthesis-protocol.md         # как сводить отзывы в единый отчёт
        report-templates.md           # шаблоны md + self-contained html + инфографика
        determinism.md                # правила воспроизводимости: канонизация, сид, схемы
```

Команда — тонкий вход; вся логика в скилле. Скилл вызывается и через `/persona:review`,
и напрямую через механизм Skill.

## 4. Раскладка результатов (рядом с документом)

Для входного пути `P` базовый каталог — рядом с `P`:

```
<dir(P)>/.persona-review/<slug(P)>/
  00_input-analysis.md            # саммари анализа входа (фаза 2-3)
  personas/
    persona-set.json              # кэш-ключ + content-hash + канонизированные параметры
    01_<имя>.md ... NN_<имя>.md   # профили персон (роль, компания, lens, "боль")
  runs/<YYYY-MM-DD_HHMM>/
    thinking/                     # промежуточные размышления, сырые выводы ревьюеров (JSON)
  reports/
    persona-feedback.md           # отзывы всех персон (финальный артефакт)
    persona-feedback.html         # то же + инфографика
    synthesis.md                  # сводный отчёт (финальный артефакт)
    synthesis.html                # сводный + инфографика, вход для других пайплайнов
```

- `slug(P)` — kebab-case от имени файла/папки.
- `personas/` = кэш. При повторном `/persona:review` на тот же путь предлагается переиспользование.
- Если вход — папка, `dir(P)` = родитель папки, `slug(P)` = имя папки.

## 5. Пайплайн (фазы)

### Фаза 1. Вход и валидация
Команда **обязательно** требует путь (файл или папку). Если не указан — останавливается с
просьбой указать путь. Не угадывает.

### Фаза 2. Анализ входа
Прочитать вход (для папки — все релевантные файлы). Определить: **тип документа**, **язык**,
заявленную аудиторию, ключевые тезисы, объём. Язык всех отчётов = язык документа (auto-detect).
Вычислить `content-hash` входа.

Для **больших/разметочных входов (HTML, веб-страницы)** сначала извлечь читаемый текст
(убрать `<style>`/`<script>`, заменить встроенные iframe `srcdoc` плейсхолдером, снять теги,
раскодировать сущности), сохранить в `runs/<ts>/thinking/<basename>-extracted.txt` и анализировать
(и далее кормить ревьюеров) из него — CSS и встроенные макеты это шум.

### Фаза 3. Саммари + проверка кэша
Показать пользователю краткую сводку анализа (1 экран). Затем проверить `personas/`:
- **Нет кэша** → перейти к фазе 4.
- **Есть кэш, content-hash совпадает** → показать состав персон, предложить:
  переиспользовать / догенерировать ещё N / собрать заново.
- **Есть кэш, content-hash изменился** → предупредить: «контент документа изменился, персоны
  подбирались под прошлую версию», предложить: перегенерировать / переиспользовать как есть.

### Фаза 4. Интерактивные вопросы (по одному, структурный выбор)
На основе анализа пайплайн **предлагает** дефолтные варианты (выбор из списка + «другое»),
а не спрашивает с нуля. Порядок:
1. **Аудитория и цель** (свободный текст, СПРАШИВАЕТСЯ ПЕРВЫМ) — «кто читает документ и зачем?».
   Самый влиятельный ввод: один и тот же документ глазами внешних покупателей и глазами
   внутренних распорядителей бюджета даёт совершенно разных, гораздо более полезных персон.
   Ответ формирует предлагаемые ниже секторы/роли и рамку ревью; хранится как `audience_purpose`
   в `canonical_params`.
2. **Секторы / типы компаний** — предложенный список под тип документа и аудиторию, множественный выбор.
3. **Возраст и социальные группы** — предложенные диапазоны/группы.
4. **Роли** — предложенный набор под тип документа и аудиторию, пользователь правит.
5. **Сколько персон** (в штуках).
6. **Уровень враждебности** (1-5, см. фазу 6 / reviewer-protocol).

Все ответы **канонизируются**: нормализация регистра/пробелов, сортировка списков, маппинг
в фиксированный словарь секторов/ролей из `persona-archetypes.md`. `audience_purpose` —
свободный текст, канонизируется только trim/collapse/lowercase для ключа. Канонизированный набор
(`sectors`, `social_groups`, `roles`, `audience_purpose`; БЕЗ `persona_count` и уровня
враждебности) + путь = **кэш-ключ**.

### Фаза 5. Генерация персон
Детерминированно из канонизированных параметров через таблицы архетипов. **Сид** = хэш(путь +
канонизированные параметры) управляет выбором архетипов, имён, компаний — чтобы одинаковый
ввод давал одинаковый состав. Уровень враждебности в сид НЕ входит (это тон, не личность).
Сохранить профили в `personas/`. Показать сводку: имя, роль, компания, ключевая «боль/интерес».

### Фаза 6. Ревью
Спавн по агенту на персону (Opus) через параллельный спавн агентов (Agent/Task), по одному на персону (НЕ через Workflow — без opt-in gate). Каждый агент:
- надевает личину персоны (профиль из `personas/`),
- получает `audience_purpose` (рамку «кто и зачем читает») и документ (извлечённый текст для больших/HTML входов),
- применяет **уровень враждебности** как тон (параметр ревью, не часть личности),
- обязан вернуть рубрикатор как **структурированный JSON** (схема — в reviewer-protocol).

**Модель — всегда Opus** (ревьюеры и синтез): качество приоритетнее скорости, даунгрейд не делаем
даже на больших панелях.

**Прогресс.** Спавн N агентов печатает N технических строк запуска и затем молчит — чтобы не
создавать ощущение «зависло»: предупредить пользователя заранее про техстроки, вести watch-файл
`runs/<ts>/progress.md` с чек-листом персон и постить бегущий счётчик «✓ k/N готово» по мере
завершения.

Сырые выводы пишутся в `runs/<ts>/thinking/`. Обработка ошибок: упавший агент → `null`,
отфильтровывается; в отчёте явно отмечается, что персона N не дала ответ (без тихого замалчивания).

### Фаза 7. Сбор фидбэка
Собрать структурированные выводы всех персон в `reports/persona-feedback.md` и
`persona-feedback.html` (с инфографикой по всем персонам).

### Фаза 8. Синтез
Отдельный агент (Opus) сводит все отзывы в `reports/synthesis.md` + `synthesis.html`.
Цель — машинно/конвейерно пригодный отчёт: консенсусные боли, противоречия между персонами,
приоритизированный список того, что улучшить. Синтез следует `synthesis-protocol.md`.

## 6. Уровни враждебности (5, с чёткими поведенческими правилами)

Применяются как тон поверх готовых персон. Каждый уровень — различимый набор правил
(не размытая градация), чтобы модель надёжно их воспроизводила. Базовый инвариант на всех
уровнях: **персона — внешний человек, не в команде автора**.

1. **Нейтральный внешний эксперт.** Оценивает по делу, признаёт сильное и слабое поровну,
   улучшения формулирует как профессиональный совет.
2. **Сдержанный скептик.** Презумпция сомнения, требует доказательств; хвалит только
   действительно сильное; улучшения — что нужно, чтобы поверить.
3. **Жёсткий оппонент** (дефолт). Против по умолчанию; похвала скупая и только за объективно
   сильное; «что улучшить» = условия, при которых перестанет сопротивляться; ищет слепые зоны.
4. **Враждебный критик.** Активно ищет, к чему придраться; допускает резкие формулировки;
   улучшения — минимум, только критичные; подчёркивает риски лично для своей функции.
5. **Максимально враждебный разнос.** Ищет только плохое; отвергает по умолчанию; улучшения
   опциональны и подаются как «это даже не спасёт». Похвала почти отсутствует.

## 7. Рубрикатор отзыва (ось повторяемости, фиксированная JSON-схема)

Каждая персона заполняет одинаковую структуру:
- `verdict`: `accept` | `accept_with_conditions` | `reject` + одна фраза позиции.
- `strengths`: что объективно сильно (скупо, по делу).
- `issues[]`: каждый — `{ severity: critical|major|minor, location, problem }`.
- `conditions_to_stop_resisting[]`: конкретные условия принятия.
- `blind_spots[]`: риски/слепые зоны, которые автор не видит.
- `axis_scores`: 0-10 по осям — `clarity`, `completeness`, `realism`, `fit_to_my_interests`,
  `trust`.

## 8. Инфографика в HTML (self-contained, inline CSS/JS)

Файлы открываются standalone, без внешних ресурсов. **Каждый `.html` — полный документ,
начинающийся с `<!DOCTYPE html><html lang="ru"><head><meta charset="utf-8">…`, записанный в UTF-8.**
Без объявления кодировки кириллица в браузере читается как cp1252 → мохибейк (`Ð'ÐµÐµÑ€`); это
самый частый дефект генерируемых отчётов. Минимум графиков:
- **Тепловая карта** severity × персона (где у кого критично).
- **Гистограмма consensus pain points** (что назвали многие).
- **Веер вердиктов** (распределение accept / conditions / reject).
- **Сравнение оценок по осям** между персонами (напр. радар или сгруппированные бары).

## 9. Воспроизводимость — сводка рычагов

- Кэш персон по ключу (путь + канонизированные параметры, включая `audience_purpose`; без
  `persona_count` и уровня враждебности) → состав совпадает при переиспользовании.
- Структурный выбор параметров + канонизация → одинаковый ввод формально одинаков.
- Сид = хэш(путь + канон. параметры) → детерминированный выбор архетипов/имён/компаний.
- Жёсткие JSON-схемы вывода у ревьюеров и синтеза.
- Промежуточные размышления на диск, не в эфемерный контекст.
- На temperature не опираемся (рычага в Claude Code нет).

## 10. Вне области (YAGNI)

- Нет внешних сервисов (Notion и т.п.) — только локальные файлы.
- Нет правки самого документа — только обратная связь.
- Нет веб-поиска — оценка идёт по содержимому документа и профилям персон.

## 11. Открытые вопросы для реализации

- Точный формат `persona-set.json` (поля кэш-ключа) — определить в `determinism.md`.
- Конкретные таблицы архетипов по типам документов — наполнить в `persona-archetypes.md`
  (расширяемо; стартовый набор покрывает ТЗ, политику ИБ, договор, регламент, маркетинг).
