# Ember Knights — «Честный урон» (BepInEx IL2CPP мод) — Design

Дата: 2026-06-28
Статус: на ревью

## 1. Цель

Мод-оверлей для Ember Knights (Unity 2022.3.62f3, IL2CPP, билд 2.3.1/4969),
который показывает **реальный текущий урон** способностей, скиллов, оружия и
артефактов **с учётом текущих статов игрока** (ATK, криты, модификаторы урона) и
текущих апгрейдов/реликвий. На экране выбора наград дополнительно показывает
**прогноз-дельту**: как предлагаемый предмет изменит урон уже имеющихся
способностей/оружия/петов (пример: «Wisp сейчас 120 → станет 168»).

Только одиночная игра или приватные лобби, где все стороны это понимают (мод
read-only по отношению к игре и сети — см. §7, но это всё равно сторонний мод).

## 2. Требования

### Функциональные
- F1. Показывать честный урон на **окне информации оружия** (`UIWeaponInfo*`).
- F2. Показывать честный урон в **инвентаре/паузе** для экипированных абилок,
  скиллов и реликвий, которые скейлятся со статами.
- F3. На **экране выбора наград** (`UIItemSelect*`): для предлагаемого предмета
  показывать его собственный честный урон И **прогноз влияния** на текущие
  способности/оружие/петов.
- F4. Учитывать все источники статов: оружие, реликвии, апгрейды абилок, древо
  эмберов, стат-гемы (всё, что попадает в список модификаторов игрока).
- F5. Формат вывода — **аддитивная строка-суффикс** рядом с оригиналом
  (например `≈ 247 урона (с учётом статов)`); оригинальный текст не изменяется.
- F6. Горячая клавиша вкл/выкл оверлея; опции в конфиге BepInEx.
- F7. Встроенный **диагностический логгер** (см. §5) — основной механизм
  калибровки и проверки.

### Нефункциональные
- N1. **Fail-safe**: любой хук обёрнут в try/catch; ошибка мода никогда не роняет
  игру и не прерывает геймплей. При исключении — лог и тихий пропуск.
- N2. **Read-only по отношению к игре**: мод не пишет в игровое состояние и не
  отправляет сетевых сообщений (никакой мутации живого стейта даже для прогноза).
- N3. Совместимость с конкретным билдом игры; при несовпадении сигнатур —
  деградация с логом, а не краш.

## 3. Архитектурное решение (выбранный подход «A»)

Формулы урона нет в IL2CPP-дампе (только сигнатуры + RVA, без тел методов), а
прогноз-дельта требует гипотетического пересчёта, которого игра сама не делает.
Поэтому:

- **Резолв статов реплицируется в моде.** Игрок хранит список рантайм-
  модификаторов `XAttribModifier { eAttrib Attrib; float Value; eAttribModOperator
  Operator; ... }` с предикатами `IsADD`/`IsMUL`. Мод читает этот список + базовые
  значения и сам агрегирует (ADD/MUL) → итоговые `eAttrib`. Для прогноза в скретч-
  расчёт добавляются модификаторы, построенные из предлагаемого предмета через
  конструктор `XAttribModifier(XAttribModDef Def, int UpgradeCount, ...)`.
- **Урон считается как** `base(из XDef) × релевантные резолв-статы`. Маппинг
  «какой стат на что влияет» выводится из имён `eAttrib` (`ATK`, `CritChance`,
  `CritDmgMUL`, `SpellDamageModifier`, `AbilityNumHitsModifier`,
  `ThrowDamageModifier`, `BonusBurnDamageModifier`, `FinalPlayerDamageMultiplier`
  …) и **калибруется** по диагностическим логам.
- **Read-only хуки на расчёт урона игры** используются только для **калибровки**:
  сравнить «число мода» с фактическим числом игры и подогнать константы. Это не
  путь получения данных для UI (он не даёт гипотетику), а инструмент проверки.

Отвергнутые альтернативы:
- B (только перехват готовых значений игры) — не даёт прогноз-дельту.
- C (временно применить модификатор к живому игроку и прочитать) — мутирует
  сетевой стейт; риск рассинхрона; нарушает N2.

## 4. Компоненты (единицы с одной ответственностью)

1. **`Plugin`** (`BasePlugin`): точка входа, конфиг, инициализация HarmonyX,
   регистрация хоткеев, общий guard-логгер.
2. **`PlayerLocator`**: находит локального игрока (`GameCode.XEntity` /
   `PlayerStateCMP`) и его компонент атрибутов. Кэширует, инвалидация по сменам
   состояния/комнаты.
3. **`AttribResolver`**: вход — список `XAttribModifier` + база; выход — резолв-
   значения `eAttrib`. Метод `Resolve()` и `ResolveWith(extraMods)` для what-if.
   Чистая функция, юнит-тестируема в отрыве от игры.
4. **`DamageCalculator`**: вход — игровой `XDef` (оружие/абилка/скилл/реликвия/
   пет) + резолв-статы; выход — числовой урон. Здесь живут калибровочные
   константы и маппинг attrib→эффект. Чистая, тестируемая.
5. **`Diagnostics`**: пишет лог-файл (см. §5); содержит read-only Harmony-хук на
   игровой расчёт урона для сверки.
6. **UI-инъекторы** (Harmony postfix, по одному на поверхность, каждый
   изолирован):
   - `WeaponInfoInjector` → `UIWeaponInfo*`
   - `InventoryInjector` → панели паузы/инвентаря
   - `RewardSelectInjector` → `UIItemSelect*`, с прогноз-дельтой
   Каждый инъектор добавляет дочерний TMP-лейбл/суффикс, не трогая оригинал.

Границы: инъекторы зависят от `PlayerLocator`+`DamageCalculator`+`AttribResolver`
через явные интерфейсы; расчётное ядро (3,4) не знает про Unity/UI и тестируется
отдельно.

## 5. Диагностический логгер (краеугольный камень итерации)

При активации (хоткей) пишет в `BepInEx/honest-damage-diag.log`:
- все `eAttrib` локального игрока (резолв) и сырой список `XAttribModifier`
  (Attrib/Value/Operator/Source/SourceDefId);
- экипированное оружие + его `XWeaponDef` (AttackBase, DamageType, AttribModifiers);
- активные абилки/скиллы/реликвии/петы + их дефы и `XAttribModDef[]`;
- дамп иерархии открытого UI-объекта (имена типов/полей TMP-текстов) — чтобы точно
  найти точки инъекции в рантайме;
- при срабатывании игрового расчёта урона — фактическое число (для калибровки).

Пользователь запускает, присылает лог; по нему калибруются `DamageCalculator` и
точные селекторы UI. Так как метод-тела недоступны и игра не запускается на стороне
разработки — это и есть «верификация поведением».

## 6. Поток данных

- Открытие UI → postfix инъектора → `PlayerLocator.GetLocal()` →
  `AttribResolver.Resolve()` → `DamageCalculator.Compute(def, stats)` →
  форматирование суффикса → добавление дочернего лейбла.
- What-if: предлагаемый `def` → построить `XAttribModifier[]` из его
  `XAttribModDef[]` → `AttribResolver.ResolveWith(extra)` → пересчитать
  затронутые предметы → показать `сейчас X → станет Y` (затронут = тот, чей
  attrib-маппинг пересекается с attrib'ами предложенных модификаторов).

## 7. Сетевая безопасность (обоснование N2)

Игра хост-авторитарна; синк идёт через `NET_*`-сообщения. Мод только читает
локальные значения и рисует UI — в `NET_*`-поток ничего не пишет, живой стейт не
мутирует. Рассинхрон невозможен; ванильный клиент может подключиться (проверка
версии сверяет константу билда в нетронутом `GameAssembly.dll`, мод её не меняет).
Это обоснование, а не гарантия отсутствия рисков стороннего мода.

## 8. Сборка и зависимости

**Сборку целиком выполняет разработчик (Claude), не пользователь.** Пользователь
получает готовый загружаемый `.dll` + папку BepInEx и только копирует файлы.

- **BepInEx 6 (BleedingEdge, IL2CPP)** для Unity 2022.3 win-x64.
- **Interop-сборки генерируются офлайн** (`Il2CppAssembly-CSharp`, `Il2Cppmscorlib`,
  `UnityEngine.*`) напрямую из `GameAssembly.dll` + `global-metadata.dat` через
  пайплайн Cpp2IL → Il2CppInterop.Generator (+ Unity base libs для 2022.3.62f3) —
  **без запуска игры**. Это убирает зависимость от «запусти игру один раз».
- `.csproj` (netstandard2.1) с референсами на сгенерированные interop +
  `BepInEx.Unity.IL2CPP` + `HarmonyX` + `Il2CppInterop.Runtime`.
- `dotnet build` (dotnet 6/8/9 уже установлен) → `.dll`.

Поток установки для пользователя: распаковать готовый BepInEx в папку игры →
положить готовый `.dll` в `BepInEx/plugins/` → запустить игру.

**Граница ответственности / единственная оговорка:** Claude гарантирует
*компилируемый, загружаемый* `.dll`, но не может запустить игру и проверить
поведение. Поэтому корректность первого запуска (точная формула §3 + точные
селекторы UI §5) доводится по диагностическим логам пользователя — это
калибровка, а не сборка, и она согласована («пользователь итерирует сам»).

## 9. Тестирование

- Юнит-тесты для `AttribResolver` и `DamageCalculator` (чистые функции; проверяем
  агрегацию ADD/MUL и маппинг на синтетических данных).
- Интеграция с игрой проверяется диагностическим логом (§5) + сверкой с фактическим
  уроном игры через read-only хук.
- Все хуки fail-safe (N1): тест, что исключение в инъекторе логируется и не
  всплывает.

## 10. Известные риски и неопределённости

- Точная формула урона неизвестна → калибровка по Фазе 0; первая сборка почти
  наверняка потребует правок (пользователь итерирует сам — согласовано).
- Точные имена UI-классов/полей для инъекции уточняются рантайм-дампом.
- Множество «затронутых предметов» для what-if определяется маппингом attrib→def;
  возможны пограничные случаи (условные эффекты реликвий), которые помечаем как
  «прогноз приблизительный».

## 11. Объём первой поставки (согласовано: «всё сразу»)

Фазы 0+1+2 в одном плагине со встроенным логгером. Сборку (interop + `.dll`)
выполняет Claude; пользователь прогоняет логи и согласует калибровку.
Деливерабл: **готовый собранный `.dll`** + подготовленная папка BepInEx +
исходники + `.csproj` + пошаговая инструкция установки (копирование файлов).
