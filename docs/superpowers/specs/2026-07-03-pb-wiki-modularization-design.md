# PB-Wiki — разбиение монолита на модули

**Дата:** 2026-07-03
**Статус:** утверждён к реализации

## Проблема

`tools/pb-wiki/index.html` — монолит: 205 строк CSS + ~37 строк разметки +
~398 строк inline-JS в одном файле (45 КБ ≈ ~12K токенов). Любая правка UI
заставляет читать весь файл в контекст → дорого при разработке.

Исходная идея пользователя — «переписать на Node.js» — отклонена: токены при
правке жрёт **размер читаемого файла**, а не рантайм. Node сменил бы рантайм,
но не размер файла, и вдобавок сломал бы главное свойство инструмента —
открытие двойным кликом по `file://` (ES-модули блокируются CORS на `file://`;
Node-сервер/SSR требует запуска). Настоящий запрос — **разбить монолит на
маленькие фокусные файлы**.

## Решение: классические скрипты, без сборки, без неймспейса

### Ключевой технический факт

Классические `<script>` (без `type="module"`) на одной странице делят **общий
global lexical scope**: `const`/`let`/`function`, объявленные в одном файле,
видны в следующем. Разрезать единый `<script>` на несколько `<script src>` в
том же порядке = поведение, **идентичное конкатенации**. Перекрёстные ссылки
(`D`, `SM`, `render()`, …) переписывать не нужно.

Следствие: **неймспейс `window.PB` не вводим.** Он потребовал бы переписать
каждую ссылку (`D` → `PB.D`) — большой диф и риск ради солового офлайн-тула.
Выбираем минимальный, близкий к zero-diff разрез.

Inline-`onclick` (`resetFilters()`, `closeDetail()`, `openMod()`) продолжают
работать: это function-декларации верхнего уровня → попадают на `window`.

### Жёсткие требования

1. **Порядок подключения** сохраняется (см. ниже).
2. Строка бута `readURL(); applyURL();` остаётся **последней** исполняемой.
3. `<script src>` — классические, **не** `type="module"` (иначе CORS на `file://`).
4. `data.js` и `extract.py` не трогаем.

## Раскладка файлов

Все — в `tools/pb-wiki/`.

| Файл | Содержимое (текущие строки index.html) | ~строк |
|------|----------------------------------------|--------|
| `styles.css` | весь CSS (`<style>`, стр. 7–212) | 205 |
| `core.js` | константы + хелперы (252–260), подготовка данных BOUNDS/MNFS/CATS (262–275), state + URL (277–308), matching/counts (310–326), форматирование (499–506) | ~90 |
| `filters.js` | фасетные фильтры UI, диапазонные слайдеры, колонки (328–412) | ~85 |
| `list.js` | render, чипы, таблица, карточки, обработчики скролла (414–497) | ~85 |
| `detail.js` | детальная панель + модули (508–583) | ~75 |
| `interactions.js` | сравнение, tooltip, вкладки/вид/поиск, **бут** (585–648) | ~65 |

`index.html` схлопывается до `<head>` + `<link rel="stylesheet" href="styles.css">`
+ разметка `<body>` + ссылки на скрипты (~90 строк).

### Порядок подключения в index.html

```html
<link rel="stylesheet" href="styles.css">
...
<script src="data.js"></script>
<script src="core.js"></script>
<script src="filters.js"></script>
<script src="list.js"></script>
<script src="detail.js"></script>
<script src="interactions.js"></script>
```

## Границы модулей — почему они честные

- **core.js** — общий фундамент: данные, производные структуры, состояние,
  матчинг, форматирование. Всё, на что опираются остальные. Исполняемый на
  старте prep-блок (263–275) обязан быть здесь и до всех вызовов, использующих
  BOUNDS/MNFS/CATS — гарантируется порядком (core.js первый после data.js;
  функции-потребители вызываются лишь из бута в конце).
- **filters.js** — левая панель: построение групп, слайдеры, счётчики фасетов,
  выбор активных колонок. `const COLLAPSED` живёт здесь (используется только тут).
- **list.js** — центральная область: список, сортировка, чипы активных
  фильтров, рендер таблицы и карточек.
- **detail.js** — правая панель: карточка предмета (уровень, редкость, слоты) и
  карточка модуля.
- **interactions.js** — сквозные взаимодействия и точка входа: сравнение,
  tooltip, вкладки/вид/поиск, `applyURL`, финальный `readURL(); applyURL();`.

Разлёт немедленно-исполняемых `addEventListener` по файлам безопасен: все
целевые DOM-элементы существуют (скрипты в конце `<body>`), а функции-обработчики
вызываются только по действию пользователя — к тому моменту определены все файлы.

## Что НЕ делаем (YAGNI)

- Не вводим неймспейс/модульную систему.
- Не добавляем шаг сборки, бандлер, Node, npm.
- Не дробим CSS на под-файлы (один `styles.css` уже даёт нужный выигрыш;
  CSS правится секциями редко).
- Не рефакторим логику и не переименовываем — только перенос кода.

## Верификация (обязательна — это рефактор с сохранением поведения)

Открыть `index.html` двойным кликом и прогнать до/после — идентично:

1. Фасетные фильтры + динамические счётчики; сброс.
2. Диапазонные двойные слайдеры (drag, коммит, обновление счётчиков).
3. Переключение таблица ⇄ карточки.
4. Сортировка по колонкам (клик, реверс).
5. Деталь: слайдер уровня (пересчёт статов), переключатель редкости (слоты).
6. Вкладка «Модификации» + открытие модуля.
7. Сравнение: выбор ≥2, модал, лучшее/худшее.
8. Tooltip при наведении.
9. Поиск (`/` фокус, дебаунс, счётчики).
10. **URL-состояние round-trip:** выставить фильтры/сорт/открытый предмет →
    скопировать URL → перезагрузить → состояние восстановлено; «Назад» работает.

Консоль браузера — без ошибок (ReferenceError при неверном порядке всплыл бы тут).

## Риски

- **Неверный порядок скриптов** → ReferenceError на старте. Митигируется явным
  порядком выше + проверкой консоли.
- **Случайный перенос function → const-выражение** сломал бы `window.*` для
  inline-onclick. Митигируется правилом «только перенос, без переписывания форм
  объявлений».
