## 1. Контекст и формулировка задачи

### 1.1 Что происходит

Primo AI Server — on-premise платформа для интеллектуальной автоматизации. Сегодня в продукте работают два зрелых блока: Умный OCR (обработка документов) и AI Text (обработка текста). Оба продаются.

Следующий шаг — ИИ агенты двух типов:

- **Сценарные ИИ агенты** (цель Ц1-2 в стратегическом документе) — набор шагов определён заранее, LLM работает внутри шагов: понимает запрос, отвечает по корпоративным знаниям, выполняет действие. Предсказуемы и управляемы. Статус: "начинаем продавать".
- **Автономные (рассуждающие) ИИ агенты** (цель Ц1-3) — сами прокладывают путь решения. Выбирают шаги, вызывают инструменты, действуют. Статус: архитектура, план на Q4 2026.

### 1.2 Решение руководства

ИИ агентов выносят как отдельные продукты в отдельную команду разработки с последующей интеграцией в общий скоуп продуктов Primo RPA.

### 1.3 Задача команды

Спроектировать и построить платформу для обоих типов агентов. Начать с MVP за 3-4 недели, запустить пилоты и пресейлы в кратчайшие сроки.

### 1.6 Что блокирует AI-сервер сегодня и роль агента

В стратегической документации зафиксированы **4 основных кейса, которые AI-сервер в текущем виде не закрывает**. Их объединяет общий разрыв: AI-сервер умеет обрабатывать документ (OCR, классификация, извлечение данных), но **не умеет дальше загружать результат в смежные системы** (1С, ERP, почта, файловые хранилища и т.п.). Именно это «доведение результата до целевой системы» и есть задача AI-агента.

Ключевой вывод по приоритетам:

- **Сам агент и языковая модель для PoC могут быть практически любыми** — это не блокер. Для проверки гипотезы достаточно внешнего агента и внешней модели (см. §2.3).
- **Единственный реальный блокер — отсутствие MCP к AI-серверу и его компонентам.** Пока AI-сервер (OCR, NLP, выдача обработанных документов) не выставлен наружу как MCP, агенту не на что опираться. Поэтому разработка MCP к AI-серверу выносится в **нулевую фазу роадмепа** (§10).

## 2. Общая архитектура платформы

Ключевая идея: оба типа агентов — это разные **стратегии исполнения** поверх единой платформы. Платформа предоставляет общую инфраструктуру, а тип агента определяет только логику выбора следующего шага.

### 2.1 Схема компонентов

```
┌─────────────────────────────────────────────────────┐
│                   Chat UI (React)                   │
├─────────────────────────────────────────────────────┤
│                   API Gateway (Go)                  │
│            auth · rate-limit · routing              │
├──────────────┬──────────────────────────────────────┤
│              │       Agent Runtime (Python)         │
│  Agent       │  ┌────────────┐  ┌────────────────┐  │
│  Registry    │  │ Scenario   │  │  Autonomous    │  │
│  & Config    │  │ Executor   │  │  Executor      │  │
│              │  │ (граф)     │  │  (ReAct loop)  │  │
│              │  └─────┬──────┘  └───────┬────────┘  │
│              │        └────────┬────────┘           │
│              │         ┌──────┴───────┐            │
│              │         │  MCP Router  │            │
├──────────────┘         └──────┬───────┘            │
```

### 2.2 Компоненты и стек

| Компонент | Язык | Назначение |
|-----------|------|-----------|
| **Desktop Client** | Electron/Tauri + React | Десктопное приложение: пользователь запускает агента в режиме чата прямо на рабочем месте (§10, Фаза 1) |
| **API Gateway** | Go | Единая точка входа: аутентификация, роутинг, rate limiting |
| **Agent Runtime** | Python | Ядро исполнения агентов. Два executor'а с общим интерфейсом |
| **MCP Router** | Python | Единый реестр MCP-серверов. Агент вызывает инструмент по имени, роутер маршрутизирует в нужный MCP-сервер |
| **LLM Provider** | Python | Абстракция над LLM: Claude (PoC), AI Server, Ollama, vLLM. Единый интерфейс. Цель — собственная модель (§5.5) |
| **State & Durable Execution** | Python + очередь задач (Celery / durable-execution) | Состояние сессии, история диалога, **долгоживущие приостанавливаемые процессы** между шагами (§3.5) |
| **Governance** | Go | RBAC, аудит-лог, guardrails |
| **Chat UI** | React/TypeScript | Чат с агентом, трейс рассуждений, журнал шагов (web + основа десктоп-клиента) |
| **MCP-серверы (инструменты)** | Python | Конкретные интеграции как MCP-серверы: **MCP к AI-серверу** (OCR/NLP/выдача документов), 1С, почта, RAG, RPA. Каждый требует предметной экспертизы (§4) |

**Принцип разделения Go/Python:** Go — инфраструктура (API, auth, governance). Python — AI-логика (runtime, MCP-серверы, LLM). Чёткая граница, минимум пересечений.

**Важно про терминологию:** то, что в ранних версиях документа называлось «tools / коннекторы», по факту является **MCP-серверами**. Это не косметика: разработка каждого MCP-сервера требует экспертизы в предметной области (как устроен AI-сервер, 1С, конкретная ERP), а не только инженерной. Это влияет на оценку трудозатрат и на то, кого подключать к разработке каждого коннектора.

### 2.3 Архитектура PoC

Для PoC-фазы сознательно берём готовые внешние компоненты — цель проверить гипотезу и снять блокер, а не строить финальный стек. Состав PoC:

```
┌──────────────────────────────────────────────────────────┐
│   Десктоп-клиент / Chat UI  (чат на рабочем месте)        │
└───────────────────────────┬──────────────────────────────┘
                            │
                  ┌─────────▼──────────┐
                  │   Claude — агент    │  ◄── ReAct / сценарий
                  │  (Claude Agent SDK) │
                  └────┬───────────┬────┘
        LLM-вызовы     │           │   вызовы инструментов
            ┌──────────▼──┐    ┌───▼──────────────┐
            │ Claude       │    │ MCP к AI-серверу │ ◄── ГЛАВНЫЙ
            │ (модель)     │    │ (OCR/NLP/докум.) │     блокер
            └──────────────┘    └───┬──────────────┘
                                    │
                              ┌─────▼──────┐
                              │ AI-сервер   │
                              └─────────────┘
                 + по мере надобности: MCP к 1С, почте, RAG
```

| Компонент PoC | Чем закрываем | Статус |
|---------------|---------------|--------|
| AI-сервер | Существующий продукт (OCR, NLP) | Есть |
| **MCP к AI-серверу** | Разрабатываем (нулевая фаза) | **Блокер** |
| Агент | **Claude** (Claude Agent SDK) | Внешний, на PoC |
| Языковая модель | **Claude** | Внешний, на PoC |
| Клиент | Десктопное приложение / чат | Фаза 1 |

Почему так: агент и модель на PoC не критичны и заменяемы (см. §1.6), поэтому берём самый быстрый путь к работающей демонстрации — Claude и как агент, и как модель. Всё, что отделяет PoC от продукта, — это абстракции LLM Provider (§5) и MCP Router (§4), которые позволяют позже подменить Claude на собственные агент и модель **без переписывания бизнес-логики** (§5.5).

## 3. Agent Runtime — движок исполнения

### 3.1 Общий интерфейс

```
AgentExecutor:
  input:  UserMessage + Context + ToolRegistry
  output: stream of AgentEvent (thought, tool_call, tool_result, answer, approval_request)
```

Все события — единый поток `AgentEvent`. UI, логирование и governance работают одинаково для обоих типов агентов.

### 3.2 Scenario Executor

```
                    ┌──────────────┐
                    │  Step Graph   │
                    │  (YAML/JSON)  │
                    └──────┬───────┘
                           │
              ┌────────────▼────────────┐
              │    Step 1: classify     │
              │    LLM: "определи тип  │
              │    документа"           │
              └────────────┬────────────┘
                      ┌────┴─────┐
                 invoice?     contract?
                      │          │
              ┌───────▼──┐  ┌───▼────────┐
              │ Step 2a:  │  │ Step 2b:   │
              │ extract   │  │ summarize  │
              │ requisites│  │ terms      │
              └───────┬───┘  └───┬────────┘
                      └────┬─────┘
              ┌────────────▼────────────┐
              │  Step 3: action (1С)    │
              │  human approval: true   │
              └─────────────────────────┘
```

- Граф шагов определяется в YAML/JSON (позже — через визуальный конструктор)
- Каждый шаг: prompt для LLM + допустимые tools + условия перехода
- LLM работает **внутри** шага, но не выбирает следующий шаг
- Детерминированный маршрут, предсказуемое поведение

### 3.3 Autonomous Executor

```
         ┌──────────────────────────┐
         │   System Prompt +        │
         │   Task Description +     │
         │   Available Tools        │
         └────────────┬─────────────┘
                      │
              ┌───────▼───────┐
              │   THINK       │◄── LLM рассуждает о следующем шаге
              └───────┬───────┘
                      │
              ┌───────▼───────┐
              │   ACT         │◄── вызов tool
              └───────┬───────┘
                      │
              ┌───────▼───────┐
              │   OBSERVE     │◄── оценка результата
              └───────┬───────┘
                      │
                 ┌────┴────┐
            задача     нужен ещё
            решена?    шаг?
                 │          │
          ┌──────▼──┐  ┌────▼─────┐
          │ ANSWER  │  │ THINK    │──► повтор цикла
          └─────────┘  └──────────┘
```

- ReAct-цикл: Think → Act → Observe → (repeat or Answer)
- LLM сам выбирает, какой tool вызвать и когда остановиться
- Human-in-the-loop: настраиваемый — на каждом действии, только на критических, или только на финальном результате
- Ограничения: макс. число шагов, запрещённые действия, таймаут

### 3.4 Общие компоненты (реализуются один раз)

| Компонент | Описание |
|-----------|----------|
| **ToolRegistry** | Реестр доступных инструментов с описаниями для LLM |
| **ContextManager** | Управление контекстом: история, промежуточные результаты, файлы |
| **EventStream** | Единый поток событий (thought, tool_call, result, approval) |
| **HumanApproval** | Механизм запроса подтверждения у оператора |
| **GuardrailsEngine** | Проверка действий агента перед исполнением |
| **SessionStore** | Персистентное состояние сессии. **Не сводится к таблице в PostgreSQL** — см. §3.5 |

### 3.5 Хранение состояний между шагами — ключевая сложность

Это, по итогам обсуждения, **самая тяжёлая часть сценарного агента — возможно, более сложная и комплексная, чем кажется сейчас.** Выделяем её отдельно, потому что от выбора здесь зависит вся архитектура runtime.

**Почему состояние вообще нужно хранить.** Шаги агента — не одна непрерывная транзакция. Между ними возможны:

- **Human-in-the-loop** — процесс ждёт решения человека (минуты, часы).
- **Длинные фазы ожидания** — процесс может длиться **дни, недели, месяцы**. Канонический пример — AI-онбординг нового сотрудника: шаги растянуты на весь испытательный срок.

Значит, процесс должен уметь **приостанавливаться и возобновляться** спустя произвольное время, переживая рестарты сервиса. Это задача durable-execution (долгоживущего исполнения), а не просто «сохранить контекст диалога».

**Почему PostgreSQL «в лоб» — плохая практика здесь.** Соблазн хранить состояние как строки/JSON в Postgrese велик, но у нас **неопределённость в том, какие именно процессы у нас будут и какие состояния для них нужно хранить**. Проектировать жёсткую схему под неизвестные процессы — значит почти гарантированно её ломать и мигрировать. Нужен слой, который управляет состоянием и переходами как первоклассной сущностью, а не самописная машина состояний поверх таблиц.

**Направление — очередь задач / durable-execution.** Базовый кандидат — **Celery** или **более верхнеуровневые инструменты на его базе**: они дают отложенные задачи, ретраи, расписания, что закрывает «ожидания» и частично HITL.

**Риск, который фиксируем прямо.** У Celery есть глобальная проблема — сложность. Использовать его «в сыром виде» под долгоживущие приостанавливаемые процессы — это риск **упороться**: написать поверх него самодельный движок состояний и утонуть в нём. Поэтому:

- либо берём обёртку/оркестратор поверх Celery, скрывающую сложность;
- либо отдельно оцениваем purpose-built durable-execution движки (класс инструментов, где приостановка/возобновление процесса — встроенная функция, а не то, что мы дописываем сами).

Конкретный выбор — развилка для техдира (§11). Главное решение этого раздела: **состояние и долгоживущие процессы строим на готовом движке, а не пишем с нуля поверх PostgreSQL.**

## 4. Слой MCP-серверов и интеграции

То, что раньше называлось «tools / коннекторы», — это **MCP-серверы**. Агент общается с интеграциями по протоколу MCP; добавление новой интеграции = новый MCP-сервер, зарегистрированный в MCP Router. **Каждый MCP-сервер требует предметной экспертизы** в своей области (устройство AI-сервера, 1С, конкретной ERP), поэтому разработка коннекторов — это не только инженерная, но и доменная задача.

### 4.1 Контракт MCP-сервера

```
MCP Tool (в составе MCP-сервера):
  name: str                  # уникальный идентификатор
  description: str           # описание для LLM
  parameters: JSONSchema     # входные параметры
  requires_approval: bool    # нужно ли подтверждение оператора
  invoke(params) → Result    # вызов через MCP (sync / async)
```

Агент не знает деталей реализации интеграции — он вызывает инструмент MCP-сервера по имени. MCP Router маршрутизирует вызов в нужный сервер. Это даёт совместимость со стандартом и позволяет переиспользовать чужие MCP-серверы.

### 4.2 Интеграции (MCP-серверы)

| MCP-сервер | Что делает | Фаза |
|------|-----------|------|
| **MCP к AI-серверу** | Доступ к OCR/NLP/выдаче обработанных документов AI-сервера. **Критический блокер всего продукта.** | **Фаза 0 (нулевая)** |
| **1С (REST/OData)** | Чтение справочников, документов, контрагентов. Создание/проведение документов. Загрузка обработанных документов. | PoC / MVP |
| **Email (IMAP/SMTP)** | Чтение входящих, парсинг вложений, отправка ответов. | PoC / MVP |
| **RAG / Document Search** | Поиск по загруженным документам. Векторный поиск + цитирование со ссылкой на источник. | MVP |
| **RPA Robot (MCP)** | Вызов RPA-робота для действий в системах без API. | Post-MVP |
| **HTTP / REST** | Универсальный MCP-сервер для вызова произвольных API. | Post-MVP |
| **File System** | Чтение/запись файлов, работа с сетевыми папками. | Post-MVP |

**Почему MCP к AI-серверу — нулевая фаза.** Все 4 нерешённых кейса (§1.6) упираются в одно: обработанный AI-сервером документ нужно довести до целевой системы, а для этого агенту нужен программный доступ к AI-серверу через MCP. Пока этого MCP нет, любой агент (хоть Claude, хоть собственный) бесполезен. Поэтому он идёт раньше всего остального.

### 4.3 RAG-подсистема

```
Документы ──► Chunking ──► Embedding ──► Vector Store (pgvector)
                                            │
Запрос агента ──► Embedding ──► Search ─────┘
                                    │
                              Top-K chunks ──► LLM ──► Ответ со ссылкой на источник
```

- **Vector Store:** pgvector (PostgreSQL, уже в стеке)
- **Embedding:** локальная модель (e5, BGE) через LLM Provider абстракцию
- **Chunking:** по документам, с сохранением метаданных (источник, страница, дата)
- **На выходе:** ответ + цитата + ссылка на источник (требование enterprise-заказчика)

### 4.4 Интеграция с 1С

```
Agent ──► MCP Router ──► 1C MCP-сервер ──► 1C REST API (OData)
                                              │
                                        ┌─────┴──────┐
                                        │ Справочники │
                                        │ Документы   │
                                        │ Регистры    │
                                        └─────────────┘
```

- 1С 8.x публикует OData-интерфейс из коробки
- MCP-сервер предоставляет агенту высокоуровневые операции: `find_partner`, `get_invoice`, `create_document`, `post_document`
- Агент не знает про OData — вызывает инструмент по имени с параметрами, MCP-сервер транслирует в запрос

## 5. LLM Provider — абстракция над моделями

### 5.1 Схема

```
┌─────────────────────────────────────┐
│          Agent Runtime              │
│   llm.chat(messages, tools)         │
│   llm.embed(text)                   │
└──────────────┬──────────────────────┘
               │
       ┌───────▼────────┐
       │  LLM Provider  │
       │  Interface     │
       └───────┬────────┘
               │
    ┌──────────┼──────────┬──────────────┐
    │          │          │              │
┌───▼───┐ ┌───▼───┐ ┌────▼────┐  ┌─────▼─────┐
│Claude │ │  AI   │ │ Ollama/ │  │Собственная│
│       │ │Server │ │  vLLM   │  │  модель   │
└───────┘ └───────┘ └─────────┘  └───────────┘
  PoC       prod      prod         цель (§5.5)
```

### 5.2 Интерфейс

| Метод | Назначение |
|-------|-----------|
| `chat(messages, tools?, stream?)` | Генерация: рассуждение, ответ, вызов tools. Поддержка tool calling и streaming. |
| `embed(text) → vector` | Векторное представление для RAG. |

### 5.3 Конфигурация

```yaml
llm:
  provider: claude           # claude | ai_server | ollama | vllm | own
  model: claude-opus-4-x     # на PoC
  
  embedding:
    provider: ollama
    model: bge-m3
```

Переключение провайдера — одна строка в конфиге, код агента не меняется. Это и есть механизм перехода с Claude (PoC) на собственную модель (§5.5).

### 5.4 Ограничения

- Не все провайдеры поддерживают tool calling нативно. Fallback: prompt-based tool calling (парсинг JSON из ответа LLM).
- Streaming: нормализуется абстракцией для единообразного UX.

### 5.5 Целевое состояние: собственные агент и модель

На PoC и агент, и модель — внешние (Claude, см. §2.3). Это сознательный временный выбор ради скорости. **В дальнейшем и агент, и языковые модели должны стать собственными.** Архитектура заложена так, чтобы этот переход не требовал переписывания:

| Слой | PoC | Цель |
|------|-----|------|
| Агент (логика рассуждения/сценария) | Claude Agent SDK | Собственный Agent Runtime (§3) |
| Языковая модель | Claude | Собственная модель через AI Server / vLLM |
| Точка подмены | — | LLM Provider (§5) + MCP Router (§4) |

Что это значит на практике: бизнес-логика, сценарии, MCP-серверы и governance не зависят от того, кто внутри — Claude или собственная модель. Миграция = смена провайдера в конфиге + перенос логики агента в собственный runtime, без затрагивания интеграций. Риск миграции и зависимость от Claude на переходный период вынесены в §12.

## 6. Governance — контроль и безопасность

Сквозной слой, работает одинаково для обоих типов агентов. Без этого enterprise-заказчик не пустит агента в контур.

### 6.1 RBAC

```
User ──► Role ──► Permissions
                    │
         ┌─────────┼──────────┐
         │         │          │
    agents:use  tools:1c   agents:admin
                  :read     (создание/настройка)
```

- Роли и пермишены, интеграция с AD/LDAP/Keycloak (SSO)
- Разграничение: кто пользуется агентом, кто настраивает, какие tools доступны какой роли
- MVP: базовая модель (admin / operator), без SSO

### 6.2 Audit Log

Каждое действие агента — запись в лог:

```json
{
  "timestamp": "...",
  "session_id": "...",
  "agent_id": "...",
  "user_id": "...",
  "event": "tool_call",
  "tool": "1c.post_document",
  "params": { "doc_id": "..." },
  "reasoning": "Счёт сверен, расхождений нет, провожу документ",
  "result": "success",
  "approved_by": "operator@company.ru"
}
```

- Полная трассировка: от запроса пользователя до финального действия
- Для автономных агентов — цепочка рассуждений (reasoning trace)
- Хранение: PostgreSQL, retention policy настраивается

### 6.3 Guardrails

```
Agent ──► action ──► Guardrails Check ──► разрешено? ──► Tool Execution
                                              │
                                         запрещено? ──► блокировка + лог
```

- Чёрный список действий (например: "нельзя удалять документы в 1С")
- Лимиты: макс. число шагов, макс. сумма операции, таймаут сессии
- Content filtering: проверка входа/выхода LLM на чувствительные данные (PII)
- MVP: базовые лимиты (макс. шагов, таймаут). Полные guardrails — следующая фаза.

## 9. Два варианта MVP

Общая архитектура, стек и подходы не меняются. Вариант MVP определяет только, какой тип агента строим первым.

### 9.1 Развилка: фреймворк агентов

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Claude Agent SDK** | Самый быстрый путь к PoC, готовый агент + сильная модель, нативная поддержка MCP и tool calling | Внешняя зависимость, требует замены на собственное (§5.5) |
| **Кастомный runtime** | Полный контроль, нет чужих абстракций; целевое состояние | Всё пишем сами, дольше до результата |
| **LangGraph** | Зрелый, поддерживает графы и ReAct, встроенный checkpointing состояния (релевантно §3.5) | Тяжёлая зависимость, vendor lock на LangChain |
| **smolagents (HuggingFace)** | Лёгкий, минимум абстракций | Молодой проект, меньше production-кейсов |

**Рекомендация:** на PoC — **Claude Agent SDK** (быстрее всего проверяем гипотезу, §2.3). Для последующих фаз — оценить кастомный runtime / LangGraph с прицелом на собственного агента (§5.5) и на встроенную работу с состоянием (§3.5).

### 9.2 Вариант A: MVP на сценарных агентах

**Привязка к стратегии:** цель Ц1-2 (диалоговые агенты). Все способности — фаза Run.

**Скоуп (3-4 недели):**

| Неделя | Что делаем | Кто |
|--------|-----------|-----|
| 1 | LLM Provider абстракция, MCP-интерфейс, скелет API Gateway | 3 backend |
| 1 | Scaffold Chat UI (чат + лог шагов) | 1 frontend |
| 1-2 | Scenario Executor: DSL графа (YAML), движок шагов, переходы | 2 backend |
| 2 | MCP-серверы: 1С (OData), Email (IMAP/SMTP) | 2 backend |
| 2-3 | RAG: chunking, pgvector, поиск, цитирование | 1 backend |
| 3 | Интеграция: сквозной сценарий "обработка счёта" | вся команда |
| 3-4 | Базовый audit log, human approval в UI | 1 backend + frontend |
| 4 | Стабилизация, демо-сценарий, документация | вся команда |

**Демо-сценарий:** "Обработка входящего счёта" — агент получает счёт, извлекает реквизиты (через OCR/AI Server), сверяет с данными в 1С, при расхождении запрашивает подтверждение, проводит документ.

**Результат:** работающий сценарный агент, чат-интерфейс, логирование.  
**Не входит:** визуальный конструктор (только YAML), RBAC/SSO, guardrails, автономный режим.

**Риск по срокам:** движок графов с DSL, переходами и ветвлениями — 2-3 недели на двоих. Если застрянем на DSL — MVP сдвигается. Это самый тяжёлый компонент варианта A, которого нет в варианте B. **Дополнительно:** сценарный агент острее упирается в хранение состояний между шагами (§3.5) — длинные ожидания и HITL требуют durable-execution, а не таблицы в Postgres. Это усиливает оценку сложности Варианта A.

### 9.3 Вариант B: MVP на автономных агентах

**Привязка к стратегии:** цель Ц1-3 (рассуждающие агенты). Движок — фаза Discovery. Инструменты и governance — Run.

**Скоуп (3-4 недели):**

| Неделя | Что делаем | Кто |
|--------|-----------|-----|
| 1 | LLM Provider абстракция, MCP-интерфейс, скелет API Gateway | 3 backend |
| 1 | Scaffold Chat UI (чат + трейс рассуждений) | 1 frontend |
| 1-2 | Autonomous Executor: ReAct цикл, tool calling, stop condition | 2 backend |
| 2 | MCP-серверы: 1С (OData), Email (IMAP/SMTP) | 2 backend |
| 2-3 | RAG: chunking, pgvector, поиск, цитирование | 1 backend |
| 3 | Human-in-the-loop: approval UI, уровни контроля | 1 backend + frontend |
| 3 | Базовый audit log с reasoning trace | 1 backend |
| 3-4 | Демо-сценарий "разбор исключения по счёту", стабилизация | вся команда |
| 4 | Guardrails: макс. шаги, таймаут, запрещённые действия | 1 backend |

**Демо-сценарий:** "Разбор исключения по счёту" — агент получает застрявший счёт, сам решает куда смотреть: лезет в 1С за историей контрагента, проверяет условия договора, сравнивает позиции, формулирует причину расхождения, предлагает решение. Оператор видит ход рассуждения и подтверждает.

**Результат:** рассуждающий агент с видимым ходом мысли, чат-интерфейс, логирование, human-in-the-loop.  
**Не входит:** сценарный режим, визуальный конструктор, RBAC/SSO, сложные guardrails.

**Риск по срокам:** ReAct-цикл проще движка графов — ядро за 1-1.5 недели на двоих. Основной риск — качество рассуждений LLM. Митигация: на PoC/демо использовать Claude (§2.3), для production проверять собственную/локальную модель отдельно.

### 9.4 Сравнение

| Критерий | Вариант A (сценарный) | Вариант B (автономный) |
|----------|----------------------|------------------------|
| **Сложность MVP** | Выше (DSL графов) | Ниже (ReAct-цикл) |
| **Риск по срокам** | Средний (движок графов) | Низкий (код), средний (качество LLM) |
| **Wow-фактор на демо** | Умеренный | Высокий |
| **Предсказуемость демо** | Высокая | Средняя (зависит от LLM) |
| **Доверие enterprise** | Высокое | Среднее (нужен human-in-the-loop) |
| **Дифференциация на рынке** | Слабая (workflow + AI = commoditized) | Сильная (рассуждающий агент) |
| **Путь ко второму типу** | B после A — сложнее | A после B — проще (ReAct + фиксированный план = scenario) |
| **Цель по стратегии** | Ц1-2 (Run, начинаем продавать) | Ц1-3 (Discovery, проверка гипотезы) |

**Рекомендация:** Вариант B — быстрее до MVP, сильнее на демо, проще путь к добавлению сценарного режима потом. Решение за командой.

## 10. Фазы развития до конца 2026

Роадмеп пересобран по итогам встречи: впереди появляются **нулевая фаза (MCP к AI-серверу)** и **десктопное приложение**, после которых идёт прежнее тело роадмепа с адаптациями. Это снимает главный блокер (§1.6) до того, как вкладываться в остальное.

```
┌──────────┐ ┌──────────┐ ┌───────────┐ ┌────────────┐ ┌─────────────────┐
│  Фаза 0  │ │  Фаза 1  │ │  Фаза 2   │ │  Фаза 3    │ │     Фаза 4      │
│  MCP к   │ │ Десктоп- │ │  Пилот +  │ │ Production │ │ Масштаб +       │
│ AI-серв. │ │ прилож.  │ │  2й тип   │ │  Grade     │ │ свои агент/LLM  │
│ (PoC)    │ │ (чат)    │ │           │ │            │ │                 │
└──────────┘ └──────────┘ └───────────┘ └────────────┘ └─────────────────┘
  блокер       первый        тело роадмепа с адаптациями
               клиент
```

> Сроки: добавление двух фронтальных фаз сдвигает прежнюю датировку (июнь→декабрь). Конкретные даты фиксируем после оценки Фазы 0, т.к. она на критическом пути и зависит от готовности AI-сервера к выставлению MCP.

### Фаза 0 (нулевая): MCP к AI-серверу + PoC (3-4 недели)

**Цель:** снять главный блокер — выставить AI-сервер и его компоненты как MCP — и доказать связку end-to-end на одном из 4 кейсов (§1.6).

| Результат | Фаза по стратегии |
|-----------|-------------------|
| **MCP к AI-серверу** (OCR/NLP/выдача обработанных документов) | Discovery → Run |
| Связка PoC: AI-сервер + MCP + Claude как агент + Claude как модель (§2.3) | Discovery |
| Один сквозной кейс: обработанный документ доведён до целевой системы | Discovery |
| MCP к одной целевой системе (1С / почта) для «доведения результата» | Run |
| Базовый audit log | Run |

**Проверяем:** работает ли связка «AI-сервер → MCP → агент → целевая система»? Закрывает ли она хотя бы один из нерешённых кейсов?

### Фаза 1: Десктопное приложение (3-4 недели)

**Цель:** дать пользователю первый рабочий клиент — приложение, которое он запускает в **режиме чата прямо на своём рабочем месте**.

| Результат | Фаза по стратегии |
|-----------|-------------------|
| Десктоп-клиент (Electron/Tauri + чат-UI) | Run |
| Чат с агентом, трейс шагов/рассуждений | Run |
| Работа поверх связки Фазы 0 (MCP + Claude) | Run |
| Human-in-the-loop в интерфейсе | Run |
| Локальная установка на рабочем месте | Run |

**Проверяем:** можно ли показать заказчику ценность на его рабочем месте и получить интерес к пилоту? Это основной артефакт для пресейлов.

### Фаза 2: Пилот + второй тип агента (тело роадмепа, адаптировано)

**Цель:** первый пилот у заказчика + добавление второго типа агента. Здесь же впервые серьёзно решается задача хранения состояний (§3.5).

## 12. Риски

| Риск | Вероятность | Влияние | Митигация |
|------|------------|---------|-----------|
| **AI-сервер не готов быстро выставить MCP** (нулевая фаза на критическом пути) | Средняя | Высокое — блокирует весь продукт | Синхронизация с командой AI-сервера в неделю 0; начать с минимального набора операций |
| **Хранение состояний: упороться в Celery «в сыром виде»** (§3.5) | Средняя | Высокое — самописный движок состояний съедает сроки | Не писать поверх Postgres; брать обёртку/оркестратор или purpose-built durable-execution; решить развилку #3 до Фазы 2 |
| **Разработка MCP-серверов требует предметной экспертизы**, которой может не хватать | Средняя | Среднее — медленные/некачественные коннекторы | Подключать доменных экспертов по каждой системе; начинать с одной системы |
| Зависимость от Claude на PoC + риск миграции на собственные агент/модель (§5.5) | Средняя | Среднее | Абстракции LLM Provider и MCP Router изолируют замену; проверять локальную модель параллельно начиная с Фазы 2 |
| Качество рассуждений LLM на локальных/собственных моделях недостаточно | Средняя | Высокое — автономный агент не работает | Claude на PoC, параллельная проверка локальных моделей |
| 3-4 недели на фазу — недостаточно | Средняя | Среднее — сдвиг пилотов | Жёсткий скоуп, cut features а не сроки |
| Интеграция с 1С сложнее ожидаемого (нестандартные конфигурации у заказчиков) | Средняя | Среднее | Начать с типовой конфигурации, кастомизация на пилоте |
| Конкуренция с внутренней командой AI Server за скоуп | Средняя | Высокое | Чёткие границы продуктов в этом документе |

### Критерий готовности PoC (Фаза 0)

PoC считается готовым, когда отрабатывает сквозной кейс на связке §2.3:

1. Пользователь пишет задачу в чат (Claude как агент, Claude как модель)
2. Агент обращается к AI-серверу **через MCP** и получает обработанный документ
3. Агент рассуждает / выполняет шаги (видно в UI)
4. Агент доводит результат до целевой системы (1С / почта) через MCP
5. Агент запрашивает подтверждение на критическое действие, пользователь подтверждает
6. Агент выполняет действие и отвечает результатом
7. Весь процесс записан в audit log
